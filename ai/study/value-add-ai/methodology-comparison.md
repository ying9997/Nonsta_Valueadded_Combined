# AI 项目方法论对比：工程驱动 vs 内容驱动

> 背景：非标增值 SOP 引导 AI 化项目中，两种不同的推进思路对比
> 日期：2026-08-07

---

## 两条路径的本质区别

| | 工程驱动（我的路径） | 内容驱动（资深同事的路径） |
|---|---|---|
| **核心问题** | "系统怎么搭？" | "内容怎么好？" |
| **第一步证明** | 管道能跑通 | AI 能写出好 SOP |
| **起点** | 从架构/节点设计开始 | 从 10 条真实 case 开始 |
| **迭代对象** | 管道中间环节（关键词、匹配率、节点逻辑） | 最终输出质量（SOP 可读性、准确性、完整性） |
| **反馈周期** | 长（改中间环节 → 跑 eval → 还没看到最终质量） | 短（改 prompt → 立刻看 AI 输出 → 和人工比） |
| **风险** | 管道很完善但最终产出质量不确定 | 质量验证了但缺少规模化方案 |
| **适合阶段** | 质量已验证，要规模化/上线时 | 质量尚不确定，要先证明可行性时 |

---

## 工程驱动路径（我走的）

### 步骤回顾

```
1. 分析需求 → 写 plan-nonstandard-sop-guide.md
2. 设计架构 → 5 节点 workflow（validate → match → check → llm → format）
3. 实现代码 → manifest.json + nodes/*.ts + prompts/main.md + 3个KB
4. 搭测试体系 → test-flow.ts(L1) + eval-dryrun.ts(L2)
5. 找真实数据验证 → 增值单CSV 141条 + Udesk对话 489条
6. 发现 gap → 召回率33%，知识库场景名和真实数据不对应
7. 优化中间环节 → 关键词扩充，召回提升到30.5%但高置信从3→14
8. 接 LLM 跑完整链路 → 15条，SOP质量不错但有"教客户操作系统"问题
9. 优化 prompt → 修正视角，重跑验证
10. 尝试打包部署 Coze → 格式问题卡住
```

### 优点
- 产出完整的工程骨架，可复用
- 有系统的 eval 框架，能量化衡量进步
- 架构清晰，后续迭代有基础

### 缺点
- **最终质量反馈来得太晚**：走到第 8 步才第一次看到 AI 生成的 SOP
- **中间环节优化不直接改善最终输出**：关键词从33%提到30.5%，但这不等于"AI生成的SOP更好了"
- **没有和人工基线对比**：不知道 AI 输出到底比人工好还是差
- **方向感弱**：每一步都在"探索下一步该做什么"，没有全局路线图

## 内容驱动路径（资深同事的思路）

### 他的步骤拆解

```
1. 提炼知识库场景
   → 把知识库中的 SOP 模板提取出来，理解每个场景的结构

2. 历史客服交互 + prompt + 真实知识库 → 让 AI 生成
   → 拿真实的"客户输入"+"知识库模板"直接给 AI，让它生成 SOP
   → 不需要先搭复杂 pipeline，直接 LLM + 真实数据

3. AI 生成之后对比人工
   → AI 输出 vs 历史审批通过的 SOP，放一起逐条比较
   → 找到三类情况：AI更好 / 差不多 / AI更差

4. 分析 AI 做得好的 case
   → AI 比人工更好的地方，是因为什么？
     - 更结构化？（人工写得乱，AI有固定格式）
     - 更完整？（人工漏了注意事项，AI补充了）
     - 更清晰？（人工用了口语/简写，AI用了标准术语）
   → 这些"好"的模式是怎么出来的？推理链路是什么？

5. 沉淀提炼规则
   → 把"AI做得好的模式"固化为：
     - prompt 规则（"始终包含注意事项"/"引用具体SKU"）
     - few-shot 示例（用 AI 做得好的 case 作为后续的参考样本）
     - 结构模板（固定输出格式）
   → 这就是"高质量的提炼规则"

6. 验证规则的泛化能力
   → 用提炼出的规则跑更多 case，看是否稳定产出高质量 SOP
   → 稳定了 → 再考虑 pipeline 工程化
```

### 优点
- **反馈极快**：第 2 步就能看到 AI 输出质量
- **直接优化最终产出**：每轮迭代都在改善 SOP 本身
- **有明确的"好坏标准"**：人工审批通过的 SOP 就是 ground truth
- **发现惊喜**：可能发现 AI 比人工做得更好的维度
- **路线图清晰**：每一步目标明确，不需要"探索下一步做什么"

### 缺点
- 缺少工程化骨架，规模化时需要补
- 没有 eval 自动化，质量评估靠人工
- 适合验证阶段，不适合直接上线

## 为什么他的路径"有攻略感"

### 1. 闭环反馈短

```
他的闭环：输入 → AI生成 → 对比人工 → 发现差异 → 改prompt → 再生成
  ↑ 每轮 10 分钟，立即看到结果

我的闭环：改关键词 → 跑eval → 看召回率 → 还得接LLM → 还得看SOP质量
  ↑ 每轮 1-2 小时，最终质量反馈延迟
```

### 2. 优化目标直接

```
他优化的是：SOP 输出质量（客户能看懂？仓库能执行？比人工好？）
  → 这就是项目最终要交付的东西

我优化的是：匹配准确率（33% → 30.5%）、关键词覆盖、节点路由正确性
  → 这些是中间指标，不直接等于最终交付物质量
```

### 3. 心智模型不同

```
他的心智模型：
  "我要证明 AI 能比人工做得更好" → 证明了就有信心往下走

我的心智模型：
  "我要把系统搭完整" → 搭完了再看能不能work → 万一不work之前的搭建也不算浪费
```

### 4. 攻略感来源

他脑子里有一个固定的方法论框架：

```
任何 AI 内容生成项目的通用攻略：

Step 1: 收集人工基线（人做出来是什么样？）
Step 2: 让 AI 做同样的事（看AI做出来是什么样？）
Step 3: 对比找差异（AI vs 人，谁好谁差？）
Step 4: 分析好的 case（为什么好？怎么复现？）
Step 5: 固化为规则/prompt/few-shot
Step 6: 规模化验证
Step 7: 工程化上线
```

这个框架适用于几乎所有"AI替代/辅助人工内容生成"的项目。有了这个框架，拿到任何项目都知道第一步做什么。

## 合并两条路径（最优解）

两条路径不是互斥的，最优解是：

```
Phase 1（内容驱动，1-2天）
  → 直接跑 10 条 AI vs 人工对比
  → 证明 AI 能产出好 SOP
  → 提炼出"AI做得好的模式"
  → 产出：高质量 prompt + few-shot 示例 + 结构规则

Phase 2（工程驱动，已完成大部分）
  → 用 Phase 1 产出的 prompt/规则 替换现在的 prompts/main.md
  → pipeline 中间环节（match-template等）继续优化
  → 但方向明确了：优化目标是"让更多 case 走到LLM节点"
  → 产出：完整可部署的 expert

Phase 3（评测驱动）
  → 用 Phase 1 的人工基线做 ground truth
  → 自动化对比 AI 输出 vs 人工基线
  → 产出：持续回归的 eval 体系
```

**你现在的位置**：Phase 2 的工程骨架已完成。回头补 Phase 1 的质量验证即可。
