## 1. 供应链全链路智能诊断 Agent

仓内路径：

- `experts_target/`
- `experts_target/experts_recaller/`
- `experts_target/docs/`
- `experts_target_analysis/`

### 接触

这个项目里最容易看到三类结构：

- 树：知识库分类树、Expert 域分类、Agent 路由编排。
- 队列：待处理问题、Pipeline 节点、下一步 Expert 调用。
- 哈希表：intent -> Expert、参数名 -> 参数值、知识切片 key -> 内容。

### 浏览

建议先看：

- `experts_target/Readme.md`
- `experts_target/docs/project-structure.md`
- `experts_target/experts_recaller/readme.md`
- `experts_target_analysis/qa_intent_routing_vs_vector_rag.md`

### 记忆

- 树解决“分层分类”和“从总问题走到具体 Expert”的问题。
- 队列解决“多个节点按顺序处理”和“节点之间解耦”的问题。
- 哈希表解决“根据 key 快速找到 Expert、参数、知识片段”的问题。

### 理解

用自己的话说：供应链 Agent 像一个分诊台。先用树判断问题属于入库、尾程、增值还是客户服务；再把任务放进队列逐步执行；执行时用哈希表快速找到对应 Expert 和参数。

### 搭建体系

这个项目能串起：

```text
用户问题
  -> 路由树判断领域
  -> 队列安排执行顺序
  -> 哈希表定位 Expert / 参数 / KB
  -> RESTful API 调用外部能力
  -> HTTP 状态码判断调用结果
```

## 2. OpenAPI 智能查询接入

仓内路径：

- `_workflow/20260709_OpenAPI智能查询_智能体接入/`
- `experts_target/shared/winit-openapi-call/`
- `experts_target/scripts/test-winit-openapi-call.ts`

### 接触

核心概念：

- 哈希表：API 参数映射、OAuth 凭证 KV、请求头字段。
- 栈：签名计算可按步骤压入参与签名的参数，再按规则拼接。
- TCP/IP 和 TLS：请求能到达服务端、并在传输中保持安全。
- HTTP：GET/POST、幂等性、状态码。
- OAuth 2.0：授权码、access token、刷新 token。

### 浏览

建议先看：

- `_workflow/20260709_OpenAPI智能查询_智能体接入/OpenAPI智能查询_凭证与鉴权_Spec.md`
- `_workflow/20260709_OpenAPI智能查询_智能体接入/winit_openapi_cli.py`
- `experts_target/shared/winit-openapi-call/index.ts`

### 记忆

- 哈希表让参数和凭证可以按 key 取值。
- HTTP 定义请求怎么表达动作。
- OAuth 解决“谁被允许调用”的问题。
- TLS 解决“传输过程是否安全”的问题。

### 理解

用自己的话说：OpenAPI 接入不是只会发请求。它先要知道参数在哪、凭证是谁、签名怎么算，再通过 HTTP/TLS 把请求安全送到服务端，并根据状态码和响应体判断结果。

### 搭建体系

```text
CLI / Agent 输入
  -> 参数哈希表归一化
  -> OAuth 凭证读取
  -> 签名步骤组织
  -> HTTP 请求
  -> TLS 加密传输
  -> HTTP 状态码 + 响应体解析
```

## 3. 交通事故风险预测模型

仓内路径：待补。当前未在仓库中定位到明确目录。

### 接触

这个案例适合学习：

- 树：XGBoost 是多棵决策树的集成。
- 哈希表：特征名 -> 特征值，例如 `weather=rain`、`speed=80`。

### 记忆

- 决策树用特征分裂把样本分到不同叶子节点。
- XGBoost 用多棵树叠加修正误差。
- 特征工程常用哈希表管理字段和值。

### 理解

用自己的话说：模型不是凭空“预测风险”，而是把天气、道路、速度、时间等特征放进一组树里，每棵树给出一部分判断，最后组合成风险分。

### 搭建体系

```text
原始事故数据
  -> 特征哈希表
  -> 决策树分裂
  -> 多树集成
  -> 风险分
  -> 业务预警
```

## 4. B端 SaaS 触达系统

仓内路径：

- `UPUSH需求/`

### 接触

核心概念：

- 队列：消息待发送列表。
- 优先级队列：高优先级消息先发。
- 哈希表：角色标签 -> 目标人群。
- 异步 I/O：发送消息时不让主流程一直等待。
- WebSocket：实时推送。

### 记忆

- FIFO 队列适合普通消息按进入顺序发送。
- 优先级队列适合 P0/P1/P2 消息分级。
- WebSocket 适合实时触达，轮询适合低实时性场景。

### 理解

用自己的话说：触达系统的本质是“谁该收到什么、什么时候发、发失败怎么办”。哈希表找人群，队列排顺序，异步 I/O 保证系统不被发送动作卡住，WebSocket 提供实时通道。

### 搭建体系

```text
业务事件
  -> 标签哈希表匹配人群
  -> 优先级队列排队
  -> 异步 I/O 发送
  -> WebSocket / HTTP 触达
  -> 失败重试或降级
```

## 5. 库存健康度诊断报告

仓内路径：

- `Inventory_temperature_health_related/`
- `Inventory_temperature_health_related/platform/`
- `Inventory_temperature_health_related/Temperature_health_2026/`

### 接触

核心概念：

- 树：温度计矩阵 -> 场景聚合 -> 诊断结论。
- 矩阵：SKU 温度 × DOI 分层。
- 哈希表：SKU、客户、仓库、品类字段映射。
- 文件 I/O：读取 Excel/CSV，输出 Markdown/HTML/Excel。

### 记忆

- 树形结构适合表达从明细到汇总再到结论的层级。
- 矩阵适合表达两个维度交叉后的状态。
- 哈希表适合管理 SKU、客户、仓库等维度字段。

### 理解

用自己的话说：库存健康不是看一个数字，而是把 SKU 放到“温度 × DOI”的矩阵里，再按场景汇总，最后变成客户能理解的诊断和行动建议。

### 搭建体系

```text
SKU 仓明细
  -> 字段哈希表清洗
  -> 温度 × DOI 矩阵
  -> 场景聚合树
  -> 诊断结论
  -> HTML / Markdown 报告
```

## 6. 用户分层策略

仓内路径：

- `Recommended_comprehensive_solution_service_strategy/`
- `fulfillment_reports/`

### 接触

核心概念：

- 哈希表：用户画像 -> 激励系数、客户 ID -> 标签。
- 队列：广告曝光队列、触达队列。
- 批处理：定期生成客户分层和推荐结果。

### 记忆

- 用户画像通常是一个 key-value 集合。
- 分层策略是把用户按规则放入不同桶。
- 曝光队列控制触达顺序和频率。

### 理解

用自己的话说：用户分层策略不是“给所有人一样的方案”，而是先用画像哈希表识别客户类型，再决定激励、服务或触达优先级，最后通过队列控制投放节奏。

### 搭建体系

```text
客户数据
  -> 画像哈希表
  -> 分层规则
  -> 策略/激励匹配
  -> 曝光或触达队列
  -> 效果回收
```

## 横向体系

| 概念 | 它解决的问题 | 在项目中的共同模式 |
|------|--------------|--------------------|
| 树 | 层级、分类、递进判断 | Agent 路由、知识库、决策树、报告聚合 |
| 队列 | 顺序、缓冲、解耦 | Pipeline、消息触达、曝光控制 |
| 优先级队列 | 插队、分级处理 | 高优消息、紧急工单、P0 任务 |
| 哈希表 | 快速定位 | 参数、凭证、画像、标签、字段映射 |
| 栈 | 后进先出、步骤回退 | 签名流程、调用链、错误回溯 |
| 进程/线程 | 并行执行和资源隔离 | 多 Expert、批处理任务、异步节点 |
| I/O | 数据读写和等待 | 文件导入导出、接口请求、消息发送 |
| HTTP/REST | 系统间动作表达 | MCP、OpenAPI、内部服务调用 |
| TCP/IP/TLS | 网络连通和安全传输 | OpenAPI 调用、HTTPS |
| OAuth 2.0 | 授权访问 | 第三方/开放平台接口调用 |
