# 客服嵌套链路与出卡联调（给人看）

本文面向**要在 EDS 下单页侧栏测出卡 / 读页 / 点页的人**，说明：对话为什么套了好几层工作流、客户提问后怎么走、出卡联调要盯哪些格子、以及「整条复制一份接到测试 Bot」能不能隔离现网。

**前置**：第 0 步标识格式见 [`../cs-eds-page-bridge/marker/marker-format.md`](../cs-eds-page-bridge/marker/marker-format.md)。本文不教 Coze 点哪里发布，只把链路讲清楚。

| `space_id` | Coze **空间**（一个空间里可以同时放现网稿和副本） | `7417755373999767571` |

## 1. recaller 是不是「理解意图、规划任务、给专家下发」？

**对，就是这个角色。** 它不负责最终对客说话，也不负责登录是谁。

人话：客户问题已经在 Query 里被判定「需要专家」之后，recaller 拿着一份专家名单，决定先请谁、再请谁，把任务派出去，最后把专家结果收成一段摘要交给 Query。

| 项 | 值 |
|---|---|
| 画布名称 | `experts_recaller_v2_staging_D` |
| 工作流 id | [`7656806829235077126`](https://www.coze.cn/work_flow?workflow_id=7656806829235077126&space_id=7417755373999767571) |
| 在 Query 里的节点标题 | 同样叫 `experts_recaller_v2_staging_D`（节点 id `195168`） |

它**不是**按专家中文名搜索，而是：

1. 用 Query 传来的 `expert_ids`（例如 `value-add-product-recommendation`）
2. 加上自己代码节点里写死的 `release_id`（当前 D 导出里是 `rel-experts-20260626`）
3. 去飞书专家登记表查出 `coze_workflow_id`
4. 再 `POST /v1/workflow/run` 真正跑那张专家工作流

所以：**只改专家画布上的某个版本号、但登记表仍指向旧 id，对话还是打旧专家。**

Query 画布上还挂着没连线的 `experts_recaller_v2_staging_A_1`、`experts_recaller_v2_staging_F`。试运行时只看 **D**。

## 2. 为什么要套这么多层？各自干什么？

每一层只做一件别人做不了的事。套起来是为了「登录 / 问答 / 请专家 / 某一科」可以分开改、分开灰度，而不是因为技术炫技。

你看到的现网口径：

```
对话 Bot（客服-全场景-Default）
  → 对话流 cs_Bot_Client_v2p
    → Query 工作流 cs_Default_Query_v4_staging_D
      → recaller 工作流 experts_recaller_v2_staging_D
        → 各个 expert（例如增值产品推荐）
```

你计划的测试口径（名称带 `_1` 的多半是副本）：

```
测试 Bot 7680824665929056310
  → 对话流 cs_Bot_Client_v2p_1（7685975376836739124）
    → Query cs_Default_Query_v4_staging_F_1（7686361673971695625）
      → recaller 仍可能是同一张 D（7656806829235077126）← 这里最容易误伤现网
        → expert
```

### 2.1 用快递柜打比方

| 层 | 现网名字 | 人话 | 没有它会怎样 |
|---|---|---|---|
| **页面聊天窗** | EDS 侧栏 | 卖家打字的那个框 | 没有入口，后面全白做 |
| **智能客服后台** | 例如 [`cobratest-agent.winit.com`](https://cobratest-agent.winit.com) | 把侧栏消息转给某一个 Coze Bot | 绑错 Bot = 测的不是你改的画布 |
| **对话 Bot** | 客服-全场景-Default / 测试 Bot | Coze 里「这个机器人用哪张对话流」 | 后台打到现网 Bot，你怎么复制画布都测不到 |
| **对话流 Bot Client** | `cs_Bot_Client_v2p` | 认出登录的是谁、会话、要不要灰度；**出卡口令也从这里发出去** | 聊天窗不知道你是哪个客户；也发不出 `pageRead` / `renderA2UI` |
| **Query** | `cs_Default_Query_v4_staging_D` | 真正问答：改写问题、对知识库、决定要不要请专家、最后写成给卖家的话 | 不会回答业务问题 |
| **recaller** | `experts_recaller_v2_staging_D` | 请哪些专家、什么顺序、把结果收成摘要 | 永远只用死知识，不会跑增值推荐这类专家 |
| **expert** | 如增值产品推荐 | 只回答自己那一科 | 推荐 / 查单 / 诊断某一科做不了 |

**出卡、读页、点页不发生在 expert 内部「去读浏览器」。** 专家跑在 Coze 服务器上，看不见 EDS 页面。看见页面的是**前端**；Coze 只负责发出「请画卡 / 请读页」这类口令，或把口令藏在回复文本的标识里。

## 3. 客户提问之后怎么流转（只记主对话这条线）

不要去跟「新增数据 → 结束」那条绑用户的线。那条是第一次进来把客户资料写进变量，跟问答无关。

```
卖家在侧栏说话
  → 测试环境后台（cobratest-agent）转给测试 Bot
    → Bot Client 开始节点拿到 USER_INPUT 和登录信息
      →（如需）认出/绑定这个客户
      → A/B 选择器：本应灰度不同 Query；你这份 v2p_1 副本里三条分支都进了同一张 Query
      → 子流程 Query 开始真正想答案
        → query_rewrite：把口语整理成可检索的问题
        → classification：这题大概属于哪类业务
        → q_match + pre_get_solution / post_get_solution：对上知识条目，抽出 expert_ids
        → 若名单里有专家：进入 recaller
            → 查飞书登记表 → 规划队列 → 调用 expert → 收成 reply_to_user
        → A1「拼装问题资料并组织回答」：把知识 + 专家摘要写成卖家能看的话
        → Query 的「输出」节点：这句话进入聊天记录
      → 回到 Bot Client：page_intent_emit 看要不要出卡/读页
      → 要：插件 tool_call_send_page 发给侧栏
      → 不要：直接结束（普通问答）
```

侧栏里卖家看到的那句人话，来自 **Query 的输出节点**，不是 expert 结束节点原文。expert 原文会经过 recaller 总结和 A1 改写，标识很容易在这两步被吃掉。这就是第 0 步要逐格对照的原因。

## 4. 出卡 / 读页 / 点页：你真正要懂的格子

其它上百个节点（debug、stage 思考中、OMS 查单）先当背景音。联调只盯下面这些。

### 4.1 对话流 `cs_Bot_Client_v2p_1`（[`7685975376836739124`](https://www.coze.cn/work_flow?space_id=7417755373999767571&workflow_id=7685975376836739124)）

| 节点 | 作用 | 没有它 |
|---|---|---|
| 开始 | 收用户这句话、登录客户号、会话 id | 后面全没输入 |
| 绑定用户 / 变量赋值 | 让后面知道「这是哪个卖家」 | 查单、专家会缺少客户上下文 |
| **A/B** | 按账号或尾号分流到不同 Query | 现网用来灰度；**你这份 v2p_1 里三条都进同一张 Query，分流是空的** |
| **Query 子流程** | 去问答 | 没有客服答案 |
| **page_intent_emit**（代码） | 判断这轮要不要请前端画卡或读页，吐出 `function_name` + `arguments` | 侧栏永远收不到出卡/读页口令（走 tool_call_send 这条通道时） |
| **if_should_send**（选择器） | 要才发插件；普通问答跳过 | 要么每句都去动页面，要么永远不发 |
| **tool_call_send_page**（插件） | 把 `pageRead` / `renderA2UI` 发给聊天窗后台 | 前端 `queryToolCall` 轮询不到口令，卡出不来 |
| 结束 | 本轮对话流收尾 | 流程挂住 |

这三格（代码 → 选择器 → 插件）已经在 `cs_Bot_Client_v2p_1` 上。现网旧对话流 `cs_Bot_Client_v2p` / `7685663589169381391` **没有**这三格，测试 Bot 不要绑旧的。

本地接线包里，这个对话流的 Query 子流程仍写死为 `cs_Default_Query_v4_staging_F`（`7681286672969678888`），**还不是你说的 F_1**。要用 F_1，必须在对话流画布上把子流程换成 `7686361673971695625`。

### 4.2 Query `cs_Default_Query_v4_staging_F_1`（[`7686361673971695625`](https://www.coze.cn/work_flow?space_id=7417755373999767571&workflow_id=7686361673971695625)）

| 节点 | 作用 | 没有它 / 坏了会怎样 |
|---|---|---|
| `query_rewrite` | 把用户原话整理成可检索问题 | 对不上知识库 |
| `classification` | 业务分类 | 走错知识域 |
| `q_match` | 匹配知识条目（QID） | 找不到标准答案 |
| `pre_get_solution` / `post_get_solution` | 取出解决方案，并把 `sys_experts` 合成 `expert_ids` | 有知识但请不来专家 |
| **`experts_recaller_v2_staging_D`** | 请专家 | 不会跑增值推荐 |
| **A1 拼装问题资料并组织回答** | 把专家摘要改写成对客句子 | 气泡里没有人话；也最容易把标识改没 |
| Query「输出」 | 把最终句子写入聊天 | 侧栏看不到回答 |
| 若干 `tool_call_send` | 告诉侧栏「正在思考」 | 只少一个思考中状态，不影响出卡 |
| `tools_msg_cleaner` | 清对话历史里的程序符号 | 历史里可能残留 `{}` / 代码块；**不一定处理当前这句** |

### 4.3 recaller `experts_recaller_v2_staging_D`（`7656806829235077126`）

| 节点（人话） | 作用 | 没有它 |
|---|---|---|
| 写死 `release_id` 的代码节点 | 告诉登记表「用哪一批专家」 | 查表失败或召回错批次 |
| `get-expert-registry` | 按 expert_id + release_id 查飞书表，取出 `coze_workflow_id` | 有名单但打不到工作流 |
| 规划队列（Planner） | 决定请几个专家、什么顺序 | 乱请或漏请 |
| 循环里真正调用专家 | 跑专家工作流 | 专家画布永远不会执行 |
| 总结成 `reply_to_user` | 给 A1 的唯一专家摘要 | A1 看不到专家结果；**标识也常在这里被改成摘要** |

### 4.4 增值推荐 expert

结束节点有四份产出。对出卡通道，现阶段只关心 **`analysis`（人话）**。`structured` 出不去 Query 的气泡。

专家**不能**再加一个「读取 DOM 并选中产品」的 Coze 节点：它没有浏览器。正确拆法：

| 谁 | 做什么 |
|---|---|
| 专家 | 推荐哪个产品；在人话后面带标识（出卡 JSON），或让上游发出 `pageRead` |
| 前端 | 收到 `pageRead` 就读当前 EDS 页；收到 `renderA2UI` 就画卡；用户点卡上的按钮后**前端自己去点页面** |
| 下一轮用户消息 | 前端把读到的页面塞回来（对 Coze 来说就是又一句输入） |

「推荐完再选中」= 卡片按钮里写好 `operatePage`（点第几个元素），不是 expert 里长一个读 DOM 节点。

## 5. `cobratest-agent.winit.com` 是不是测试环境 EDS 下单页？

**不是下单页本身。** 它是侧栏聊天窗背后的 **智能客服后台**（前端 SDK 的 `agent.baseUrl`）。

前端说「让后端把这个 Bot 接到 cobratest-agent」意思是：

> 测试环境的聊天后台，调用 Coze 时使用测试 Bot `7680824665929056310`，不要用现网「客服-全场景-Default」。

你还需要前端另给一条 **EDS 测试下单页 URL**（卖家后台那张填增值单的页面）。聊天窗嵌在那一页上，那一页再去打 cobratest-agent。

```
EDS 测试下单页（问前端要 URL）
  → 侧栏 SDK
    → https://cobratest-agent.winit.com（聊天后台，绑测试 Bot）
      → Coze 测试 Bot 7680824665929056310
        → cs_Bot_Client_v2p_1
```

两套对不上（测试页仍打现网 agent，或测试 agent 仍绑现网 Bot），你在 Coze 里复制多少画布都看不到卡。

## 6. 你的复制思路能不能隔离现网？

**方向对：用测试 Bot + 副本画布，不要改现网 Bot 正在嵌套的那几张。**

但这**不是**上一份说明里的路径 B。

| 名称 | 实际在干什么 |
|---|---|
| 路径 A | recaller 登记表已经指向测试副本专家 → 只改那张副本 |
| 路径 B | 登记表仍指向现网专家 `7657143181591642112` → 改现网草稿或改登记表（有现网风险） |
| **你现在想的** | 测试 Bot 整条绑副本，现网 Bot 不动。叫 **整链副本** 更准确 |

### 6.1 必须打破的一个误会：「只要改 expert 的 release_id」

`release_id` **不是**专家画布上的开关，而是 **recaller 里一个代码节点写死的字符串**（D 里是 `rel-experts-20260626`），用来过滤飞书登记表。

只改专家、不改这三件事，测试 Bot 仍会打现网专家：

1. 飞书表那一行的 `coze_workflow_id` 仍是 `7657143181591642112`
2. Query 里嵌套的 recaller 仍是现网那张 `7656806829235077126`
3. 对话流里嵌套的 Query 仍是旧的 `7681286672969678888`（F）而不是 F_1

### 6.2 现网还在用的、动了就会伤现网

现网 Query `cs_Default_Query_v4_staging_D` 嵌套的就是 **同一张** recaller `7656806829235077126`。  
你的 F_1 Query 分析结论也是：真正连线的仍是这张 D。

因此：

- **只导出 zip、没有导入成新 id、也没有在 F_1 里把子流程换成新 id** → 你改的还是现网 recaller。
- zip `Workflow-experts_recaller_v2_staging_D_1-draft-7818.zip` 必须 **导入成新工作流**（得到新的 `workflow_id`），再在 F_1 画布上把 recaller 子流程指到这个新 id。

飞书专家登记表也是现网 recaller 在读的。不要改现网那一行的 `coze_workflow_id`。要隔离就：在**副本 recaller** 里换成新的 `release_id`，并在表里**新增**一批只给测试用的行（指向副本专家）。

### 6.3 建议你按这个顺序接测试 Bot（id 可以重新导入，只要不是现网那几张）

从外到内，每一层只改副本：

1. **确认测试 Bot** `7680824665929056310` 不是「客服-全场景-Default」。只给这个 Bot 绑 `cs_Bot_Client_v2p_1`。
2. **对话流 v2p_1**：把 Query 子流程从 `7681286672969678888`（F）换成 `7686361673971695625`（F_1）。
3. **Query F_1**：把 recaller 子流程从共享的 `7656806829235077126` 换成 **新导入的 recaller 副本**（7818 zip 导入后的新 id）。
4. **专家**：复制增值推荐，把测试标识贴在结束节点 `analysis`。
5. **只在副本 recaller** 里改 `release_id`（例如 `rel-marker-test-20260917`），飞书表 **新增** 对应行，`coze_workflow_id` 填副本专家 id。现网那行不要动。
6. **后台**：cobratest-agent 绑测试 Bot。现网 agent 不要绑 v2p_1。
7. **不要**在现网 `cs_Bot_Client_v2p` 的 A/B 上给自己账号分流到 F_1。那是改现网对话流。你已经有独立测试 Bot，灰度加在现网 Bot 上是多余且危险的。

你提到「灰度只给测试账号用新的 staging_D」：现网 Query 就叫 staging_D；你手里的测试 Query 叫 **F_1**。不要把 F_1 接到现网 Bot 的灰度分支上。测试账号走测试 Bot 即可。

### 6.4 第 0 步其实可以更瘦

若这一周只想证明「标识会不会被 A1 吃掉」：

- 测试 Bot → v2p_1 → F_1 就够做 Query 试运行（不经过 EDS 页）。
- 这时 **可以先不复制 recaller**，但就不要改共享 D 的任何节点。
- 专家侧用「只跑专家工作流试运行」看结束节点有没有标识；再在 F_1 试运行里看 D 的 `reply_to_user` 和 A1。共享 D 只**看**不**改**。

一旦你要改 recaller 提示词、或改它调用哪张专家，**必须先有 recaller 副本**，否则就是改现网。

### 6.5 「推荐之后加节点读 DOM 再选中」为什么不是最小改动

最小改动是：

1. 第 0 步：标识能不能活到气泡（可能结论是活不到，再选通道 A/B/C）。
2. 出卡：要么气泡里的标识给前端拆，要么继续用已经接好的 `tool_call_send`（v2p_1 上那三格）。
3. 选中：写在卡片按钮的 `operatePage` 里，前端点。

在专家工作流里加「读 DOM」节点，既读不到页面，也绕开了前端已经做好的读页/点页。那是加厚，不是最小。

## 7. 两条出卡通道，测的时候不要混在同一句验收里

| 通道 | 口令怎么到前端 | 现在状态 |
|---|---|---|
| `tool_call_send` | Bot Client 末尾插件发出 `pageRead` / `renderA2UI` | v2p_1 已接好；不依赖专家标识是否还在 |
| 标识通道 | 专家人话后面的 `<!--SIDECAR_BEGIN-->`，前端从气泡里拆 | 第 0 步就是验证它会不会被 recaller / A1 吃掉 |

第 0 步过关前，不要指望「改了专家就能在 EDS 页出卡」。若第 0 步失败，候选是：Query 出口原样带包（要改 Query，需另一次授权）、专家旁路 A1、或放弃标识改走已接好的插件。

## 9. 对话流末尾三格：结合现网流程，放这里有没有问题？

现网 Bot Client 主对话线本质是：认出登录的人 →（可选灰度）→ 把整句交给 Query → 结束。  
`cs_Bot_Client_v2p_1` 只在 Query **后面**加了：`page_intent_emit` → `if_should_send` → `tool_call_send_page`。

### 9.1 发令放在这一层，没有问题

- 现网 Query 里已经有很多同名插件，用来告诉侧栏「正在思考」。出卡/读页走**同一条插件**，前端不用新接口。
- 放在 Query **之后**，人话已经先写进聊天；卡跟在答案后面，比塞进 Query 中间更干净。
- 选择器为假就直接结束，普通客服问答不会去动 EDS 页。
- 不改现网那张巨大的 Query，测试 Bot 只绑副本对话流即可。

绑用户那条线（新增数据 → 结束）不要接这三格。A/B 灰度也不要接到插件上。

### 9.2 真正的问题：这三格现在「听不到」专家

Query 子流程对客说话，靠的是画布中间的「输出」节点写入聊天记录。**结束节点几乎不把业务字段交回 Bot Client。**

于是 `page_intent_emit` 实际只看：

- 开始节点上的 `sidecar`（一般是空的）
- 用户这句 `USER_INPUT`（卖家打的字，或前端回传的 DOM）
- 写死的短句「出卡测试」「读页测试」

所以：卖家问「该选哪个增值产品」、专家推荐完了，**这三格不会自动出卡**。管道能通（发「出卡测试」能发出口令），但接不上「专家决定出卡」这条业务。

这不是插件放错层，是 **Query 没有把「要出卡的那包数据」交出来**。

### 9.3 其它方案（只点名一条做）

| 方案 | 做法 | 适合 | 代价 |
|---|---|---|---|
| **甲（推荐，仍用这三格）** | Query 结束或会话变量**原样**带回一包 sidecar；Bot Client 末尾三格只负责转发 | 前端继续 `queryToolCall` 收口令；人话仍走 A1 | 要改 Query 出口，需点名；现网 Query 不要直接改，改副本 F_1 |
| **乙** | 三格挪到 Query 里、A1 后面 | 代码能直接看见专家/A1 文本 | Query 又大又是现网主干；和「正在思考」的插件挤在一起；副本 Query 才能动 |
| **丙** | 不用这三格；专家人话后面带标识，前端从气泡拆 | 前端愿意解析聊天文本、少改 Coze | 标识会被 recaller 总结和 A1 吃掉（第 0 步就是在验证）；卖家气泡可能闪 JSON |
| **丁（不推荐）** | 在专家工作流里发 `tool_call_send` 或读 DOM | 看起来改得少 | 专家没有浏览器；也没有 Bot Client 的会话 id 那套线；和现网分层反着来 |

不要三格 + 标识同一期混着验收。先定前端到底听插件还是听气泡。

当前已授权：测试 Bot 上**留着**这三格当发令口；业务上走方案甲——**只改副本 Query F_1** 把 sidecar 交回来，现网 Query 不动。选中与前端 catalog 对齐为 `operatePage.selectOption`（`args=[index, optionText]`，一组用 `actions`），不用 PRD 的 `fieldKey+valueCode`。卖家页气泡不许出现 JSON；Coze 预览里可以看见。
