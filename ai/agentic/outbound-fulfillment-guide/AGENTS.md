# AGENTS.md

## 关于协作者

项目主要协作者是 Henry。默认使用中文沟通，每次回复先称呼「henry」。

Henry 能理解业务流程、系统模块、接口和数据逻辑，但不默认熟悉底层代码。技术说明应先给业务结论、约束和影响，再解释实现。

## 项目目标

本项目治理「海外仓出库仓内履约」知识，为 AI Agent 和下游 Expert 提供可追溯、可验证、可版本化消费的知识产品。本次生命周期止于仓库完成出库并完成承运商或客户交接。

知识主干包括：

- 出库场景、订单类型、创建资格和字段。
- 信息、库存、费用和资格校验。
- 库存占用与分配、订单释放、波次、拣货及其异常。
- 复核、VASC、装箱、包装、打托、称重、量方、贴标和交接。
- 承运商和派送产品中仅与面单、仓库出库和交接直接相关的知识。
- 仓内异常、处理动作、SLA、费用、增值服务项和配置字段。
- 状态、对象层级、适用范围、有效期、来源和证据边界。

本项目只治理知识，不负责：

- Expert 划分、路由、Prompt、API 编排、代码节点或 Coze 工作流。
- 具体订单、包裹、客户或线上系统的实时状态存储。
- 完成交接后的轨迹、首扫、在途、派送、妥投、POD、查件、索赔和派送失败处置。
- 客户主动发起的独立退货或 RMA 完整流程。
- 系统故障、数据库、VPN 或生产运维知识。

派送型和 Non-Tracked 订单均只覆盖到有证据支持的仓库出库与交接终点；自提、销毁、下架等场景使用各自有证据的仓内终点。交接后问题必须明确说明超出当前知识库范围，不得从静态知识推断尾程结果。

## 第一性原理和对抗式审查

涉及知识模型、关系、流程、Schema、运行时切片、迁移或发布时，先判断：

1. 要回答的业务问题是什么。
2. 哪些是来源事实，哪些是解释、推导或假设。
3. 适用对象、阶段、国家、仓库、承运商、产品、时间和角色是什么。
4. 最直接、最少重复且可验证的知识结构是什么。
5. 哪些边界可能导致误路由、误召回、误披露或错误承诺。

形成方案后检查：规则冲突、旧版混用、状态域混用、对象层级错误、缺少兜底、空值误解、来源断链、敏感信息、运行时数据冒充静态事实，以及发布状态被过度声称。

复杂推理按需读取 [rules/reasoning.md](rules/reasoning.md)。

## 唯一事实源和生成边界

固定数据流为：

```text
source-references/snapshots
→ source-references/extracts 和 data/extracted
→ data/canonical/entities + data/canonical/relationships + data/canonical/vocabularies
→ domain + entities + relationship-mappings + glossary
→ index + runtime slices + release package
```

约束：

- `data/canonical/` 是实体、事实、关系和受控词表的唯一可审查事实源。
- `data/extracted/` 是候选数据，不能直接发布。
- `domain/`、`entities/`、`relationship-mappings/`、`glossary/` 和 `index.md` 是生成视图，除目录 README 外不得手工维护业务事实。
- 来源快照是证据，不是可直接修改的业务事实。
- Markdown 与 JSON 不得形成两套可分别手工修改的事实源。
- 生成视图必须带生成器、输入摘要和受控生成时间元数据。

修改 Canonical 内容后，必须运行生成、索引、覆盖、测试和校验闭环。

## 查询路由

根据用户问题起点进入，不强制套用单一路径：

| 用户问题起点 | 首要查询 | 继续交叉查询 |
|---|---|---|
| 订单类型或如何下单 | 订单类型、场景 | 前置条件、字段、仓内履约要求、限制 |
| 订单状态或状态码 | 状态实体 | 生命周期、允许动作、异常、实时数据边界 |
| 仓库正在做什么 | 生命周期、仓内任务 | 状态、SLA、异常 |
| 包装、打托、面单 | 包装模式、规则 | 对象、产品限制、费用、字段 |
| 承运商或派送产品 | 派送产品 | 只查询面单、仓库出库和交接所需的适用条件 |
| 轨迹、首扫、上网、派送、妥投 | 范围边界 | 明确交接后尾程不在本次知识库范围 |
| 异常编码或异常名称 | 异常实体 | 处理动作、角色、VASC、限制 |
| 取消、作废、改址、拦截 | 处理动作 | 只处理仓库完成交接前的状态、阶段、费用和副作用 |
| 补件或补发 | 边界消歧 | 区分补充原单资料和新建补发出库单 |
| 查件、POD、索赔或派送失败 | 范围边界 | 明确属于交接后尾程，本次不提供业务规则 |
| SLA 或多久完成 | SLA 规则 | 起终点、时区、工作日、适用范围 |
| 费用或附加费 | 费用规则 | 币种、有效期、产品、适用条件 |
| VASC、服务项、配置字段 | 对应实体 | 场景关系、字段、附件、审批 |
| API 字段或查询链路 | API 参考 | 对应业务实体；接口不能替代业务规则 |
| 具体订单或包裹现状 | 实时数据边界 | 说明需要查询的数据，不从静态知识猜测 |
| 客户主动退货或 RMA | 范围边界 | 路由到独立退货或 RMA 知识域 |

“补件”不是正式动作。来源无法证明其含义时，必须先区分：补充原单资料或新建补发出库单。任何交接后的补派或再次派送问题均按尾程范围排除。

## 回答组装

按问题需要裁剪，通常依次提供：

1. 直接结论。
2. 适用条件和证据状态。
3. 当前阶段、状态域和对象层级。
4. 可执行动作及执行角色。
5. 限制、副作用、费用或时效。
6. 需要实时查询的数据。
7. 冲突、缺口或待核实事项。

不要为了展示知识库结构而输出与问题无关的完整链路。

## 状态和对象边界

- 业务状态统一建模为 `fulfillment_status`，通过 `status_domain` 区分订单、库存作业、波次、拣货、复核、包装和交接。
- 承运商交接后的扫描和轨迹事件不进入当前状态模型。
- 主单、子单、shipment、container、包裹、SKU、仓内任务和交接记录不得混用。
- 同名状态跨系统不得静默合并，必须记录系统、原始代码、规范化含义和差异。

## 来源和证据

来源权威按问题类型判断，不设置能覆盖所有问题的单一全局顺序：

- 产品资格和限制优先当前正式产品规则。
- 客户操作步骤优先当前操作手册和实际界面证据。
- 仓内动作优先正式流程和操作 SOP。
- 状态、编码和接口字段优先当前接口文档、枚举和系统字典。
- 异常到动作必须有明确业务映射。
- 承运商和派送产品限制只治理面单、仓库出库与交接所需部分，并绑定仓库、国家、产品和有效期。
- 仓内 SLA 和费用必须有生效时间、范围、计时口径、币种和排除项。
- VASC 选择关系不能仅由接口字段存在推断。

冲突不得静默合并。记录双方来源、原文、日期、适用范围和影响；无法解决时保持 `pending_verification`，不得进入确定运行时答案。

每条 active 事实和关系必须能追溯到项目内 `source_id + sha256 + locator`。外部资料只有先进入项目内证据闭包后，才能成为正式 `source_refs`。

## 静态知识与实时数据

知识库可以说明：应查询什么、字段是什么意思、如何判断、可能执行什么动作。

知识库不得存储或猜测：具体订单状态、当前库存、费用计算结果、交接后尾程状态、线上工作流状态或客户实时数据。

需要实时数据时，明确返回所需标识符、字段和查询类型，不用静态快照回答当前事实。

## 禁止编造

不得凭经验编造：

- 订单类型、状态、事件或异常编码。
- 可取消、可作废、可拦截或可改址的仓内状态范围。
- 仓库、国家、承运商或产品支持范围。
- SLA、工作日、截单时间、费用、金额或币种。
- VASC、服务项、字段、枚举、附件和审批规则。
- 具体订单、包裹、客户或线上系统的当前事实。

知识缺失时明确说明缺少来源、实体、关系、适用范围、有效期或实时数据。

## 路径和命名

- 正式文件只使用项目内相对路径。
- 禁止写入本机盘符、用户目录、UNC、本地绝对路径、临时目录或包外运行时依赖。
- 相对路径解析后必须仍位于项目根目录内。
- 目录名和文件名使用英文小写 kebab-case；稳定业务编码可以保留原始大小写。
- 页面标题和正文可以使用中文。
- 每个业务目录必须有 `README.md`，说明定位、收录口径、子目录、生成和维护规则。
- 原始证据闭包保留在 `source-references/snapshots/<source-id>/`；原件与脱敏派生件分离。
- 文件名和目录名同样参与敏感扫描；受限原始路径不得进入 Git。

## Schema 和知识状态

新增、修改或校验业务内容前必须读取 [SCHEMA.md](SCHEMA.md)。

知识状态与业务履约状态完全分离。知识状态使用受控枚举：

- `draft`
- `pending_verification`
- `active`
- `deprecated`
- `superseded`
- `archived`

只有事实或关系自身满足 `active + runtime_eligible`、来源完整、适用范围明确、有效期合格且未被替代，才可进入 runtime profile。

页面状态不能替代事实级和关系级门禁。

## 敏感信息和披露

- 禁止提交凭证、密钥、Cookie、签名材料、真实客户、订单、地址、联系方式和未脱敏截图。
- 发现敏感原件时隔离原件，创建脱敏派生件，并记录哈希关系。
- `sensitivity` 与 `disclosure_level` 分开建模。
- `restricted` 内容不得进入一般运行时包。
- `agent_internal` 事实或关系必须有 `disclosure_guard` 和禁止披露测试。
- 对客答案不能暴露内部来源路径、接口实现、规则计算细节或内部专用入口。

## 写入和维护闭环

以下变化触发完整维护闭环：

- 新增、修改、移动、重命名或删除业务文件、来源、图片、JSON 或 CSV。
- 修改 ID、编码、状态、适用范围、有效期、来源或披露级别。
- 修改状态转换、异常处理、VASC、字段、SLA、费用或承运商关系。
- 修改 Canonical、Schema、目录、命名、标签或发布契约。

必须检查并按需更新：

1. Canonical 实体、关系和受控词表。
2. 生成的实体、流程、映射和 glossary 视图。
3. 正向和反向关系。
4. 根 `index.md` 和目录 README。
5. 来源台账、哈希、冲突和覆盖报告。
6. 检索、答案、边界和禁止披露测试。
7. [ROADMAP.md](ROADMAP.md)、[log.md](log.md) 和必要的 [CHANGELOG.md](CHANGELOG.md)。

如果对应文件尚不存在，在日志中说明，不得假装已经同步。

## 讨论与执行边界

- 讨论、规划、解释或审查时只分析，不自动修改文件。
- Henry 明确要求创建、修改、实现或修复时，才进入写入阶段。
- 大范围、跨模块、高风险或长期资产变更前，先说明范围、验证和不执行项。
- 信息不足但不影响方向时可声明假设继续；会影响范围、成本、结构或结果时先问一个关键问题。

## Git 和外部操作红线

本项目是独立 Git 仓库，父级知识库目录不得初始化为统一仓库。

以下操作必须先获得 Henry 的当次明确确认：

- 删除或移动文件、目录、证据或 Git 历史。
- 覆盖、清理或恢复工作区。
- 修改凭证、环境变量、权限或 CI/CD。
- 创建或修改远程仓库、remote 或外部系统状态。
- `git push`、rebase、强制操作、tag、release 或公开发布。
- 数据迁移、生产变更、Coze 导入/发布或线上验证。

本地实现、验证、`git status` 和本地 Git 初始化可以在已授权项目创建范围内执行。没有证据时必须区分：本地完成、已提交、已推送、已发布、已导入和线上生效。

## 多 Agent 规则

使用子 Agent 时按需读取 [rules/subagents.md](rules/subagents.md)。子 Agent 的结论必须由主 Agent结合实际文件复核，不能直接当作完成证据。

## 完成标准

任务只有在以下条件满足后才可标为完成：

- 实际文件与声明范围一致。
- 相关 Schema、路径、来源和关系校验通过。
- 生成视图与 Canonical 输入一致。
- 所需测试和敏感扫描通过。
- `ROADMAP.md` 和 `log.md` 已按规则同步。
- 明确列出本地完成、未提交、未推送、未发布和未线上验证的边界。
