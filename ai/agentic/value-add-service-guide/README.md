# 入库异常与增值服务知识库

> 面向 AI 检索和回答生成的 LLM WIKI，用于沉淀入库异常、VASC 增值产品、增值服务项（增值原子/增值事件）和配置字段之间的关系。

## 知识库目标

本知识库用于系统化沉淀「入库异常与增值服务之间的关系」。

AI 应通过本知识库回答：

- 入库异常是什么。
- 客户遇到异常后要怎么处理。
- 可以选择哪些 VASC 增值产品。
- 某个 VASC 产品下有哪些增值服务项（增值原子/增值事件）。
- 某个增值服务项需要配置哪些字段。
- 字段有哪些枚举、上传文件要求和校验规则。
- 异常、VASC 产品、增值服务项、字段之间如何互相映射。

## 设计定位

本库不是卖家端 UI 操作手册，也不是原始资料归档。

本库参考当前项目已有知识库的 LLM WIKI 模式：

- 用索引帮助 AI 快速定位文件。
- 用 Schema 约束写入方式。
- 用日志记录结构和规则演进。
- 用英文路径和稳定 slug 提升检索可靠性。
- 用显式关系映射替代隐含文档顺序。

本库的核心设计是「多入口实体关系库」。AI 可以从异常、VASC 产品、增值服务项、配置字段、流程或编码字典任意入口开始检索。

本库的维护方式是「AI 维护闭环」。新增、修改、移动或删除任何知识文件时，不依赖人工逐个提醒索引和关联文件；AI 必须根据 [AGENTS.md](AGENTS.md) 和 [SCHEMA.md](SCHEMA.md) 同步检查并更新所有受影响内容。

## 收录范围

收录：

- 入库异常定义和对客含义。
- 入库异常处理流程。
- 与入库异常处理或入库增值下单相关的 VASC 产品。
- VASC 产品下的增值服务项。
- 增值服务项的配置字段、枚举值、上传文件要求和校验规则。
- 异常、VASC 产品、增值服务项、字段之间的关系映射。
- 支撑 AI 回答所需的术语表、状态字典和编码字典。
- 可追溯的数据证据包、原始快照、规范化数据和覆盖率报告。

不收录：

- 与入库异常无关的纯出库增值。
- 卖家 UI 截图手册的全文复制。
- 系统代码、数据库、VPN、脚本、运维排查资料。
- 未确认的口头规则，除非明确标记为待核实。
- 没有索引说明、无法追溯来源、无法判断覆盖率的大体量原始材料。

## 与现有项目知识库的关系

现有项目资料可作为阅读参考输入，例如：

- `system-guide/` 中的卖家帮助中心资料。
- `kb/` 中的产品域、客服域和仓储增值资料。
- `system-team/` 中的接口、场景和编码资料。

这些资料不是正式来源标记对象。本库应从中抽取 AI 可直接推理的实体和关系，并在需要追溯时先沉淀到 `value-add-service-guide/` 内，而不是复制大段保留型文档或直接引用目录外路径。

正式来源标记只允许指向 `value-add-service-guide/` 内文件。目录外资料可以阅读和参考，但如果需要进入 `source_refs`、索引、关系映射或实体页来源，必须先沉淀到本项目目录内，便于后续只迁移 `value-add-service-guide/` 也能完整使用。

## 维护原则

1. 路径必须稳定，使用英文、小写、kebab-case，并尽量具体。
2. 文件内引用必须使用相对于 `value-add-service-guide/` 的项目内路径，便于整体迁移；不得把目录外路径作为正式来源。
3. 标题和正文可以使用中文，保留业务原称。
4. 每个业务目录必须包含 `README.md`，用于说明目录定位、收录口径和子目录。
5. 关系映射表用于判断适用性和选择逻辑。
6. 实体详情页用于解释定义、限制、字段和来源说明。
7. 接口文档可以作为来源参考，用于补充系统字段、编码、查询链路和可校验数据来源，但不直接作为业务适用性结论。
8. 数据证据包可以作为生成实体页和关系映射表的输入，但 raw 快照不可改写，覆盖率缺口不可写成不存在。
9. 新旧规则冲突时，不静默覆盖，应保留冲突并标记状态。
10. 低置信度内容必须显式标记。
11. 任何变更都必须执行 AI 维护闭环：同步检查索引、目录 README、关系映射、相关实体页、术语、来源和日志。
12. 重要结构变化或业务规则变化必须写入 [log.md](log.md)。
