# 尾程专家系统 - delivered-not-received 设计文档

## 业务场景
**妥投未收到问题处理**

客户反馈包裹系统显示已妥投，但客户实际没有收到货物，需要按照流程核实地址一致性、判断派送方式，并给出对应回复或转内部处理。

## 二、关键判断规则

### 1. 第一步：地址一致性校验

| 判断条件 | 处理方式 |
|----------|----------|
| 面单地址 ≠ 系统下单地址 | 直接报 Helpdesk 人工处理 |
| 面单地址 = 系统下单地址 | 继续判断派送方式 |

### 2. 第二步：派送方式判断（仅美国）

只有 **美国 UPS** 或 **USPS** 支持进一步自助处理，其他派送方式直接回复话术建议。

### 3. 第三步：供应商官网地址校验

| 判断条件 | 处理方式 |
|----------|----------|
| 供应商官网妥投地址 = 下单地址 → 直接回复话术 | 已核实官网一致，按标准话术回复客户 |
| 供应商官网妥投地址 ≠ 下单地址 → 进一步地理校验 | 通过谷歌地图核实地理位置 |

### 4. 第四步：片区地理位置核实

通过谷歌地图检查轨迹显示的投递 Location 和客户下单地址是否在同一地理片区：

| 判断结果 | 处理方式 |
|----------|----------|
| 在同一片区 → 回复话术 | 说明包裹已确实投递，建议客户查找周边/邻居/物业 |
| 不在同一片区 → 回复话术 | 说明地址存在偏差，建议进一步核实 |

## 三、处理节点总结

| 步骤 | 操作 | AI需获取数据 |
|------|------|--------------|
| 1 | 接收客户反馈，获取单号 | - |
| 2 | 查询出库面单地址 | 订单系统/TOM |
| 3 | 查询系统下单地址 | 订单系统 |
| 4 | 判断地址一致性 | - |
| 不一致 → | 回复话术，报Helpdesk | - |
| 一致 → | 继续判断派送方式 | 订单系统 |
| 不是UPS/USPS → | 回复话术，结束 | - |
| 是UPS/USPS → | 核实供应商官网妥投地址 | 承运商官网/接口 |
| 官网地址一致 → | 回复话术，结束 | - |
| 官网地址不一致 → | 谷歌地图地理片区校验 | 地图服务 |
| 同一片区 → | 回复话术，结束 | - |
| 不同片区 → | 回复话术，结束 | - |

## 四、需要对接的系统数据

| 数据项 | 来源系统 | 说明 |
|--------|----------|------|
| 轨迹数据（妥投状态及妥投地址） | **delivery-status**（统一获取） | 不需要本专家自行查询轨迹，复用 delivery-status 的解析结果 |
| 出库面单地址 | 订单系统 / TOM | 从面单信息中提取 |
| 系统下单地址 | 订单系统 | 客户原始下单地址 |
| 尾程派送方式 | 订单系统 / TOM | 判断是否为 UPS/USPS |
| 供应商官网妥投地址 | 承运商轨迹接口 | 获取实际派送地址（仅 US UPS/USPS 需要） |
| 谷歌地图地理校验 | 地图服务 API | 判断两个地址是否在同一片区 |
