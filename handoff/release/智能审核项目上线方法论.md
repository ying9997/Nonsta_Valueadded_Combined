# 智能审核项目上线方法论

> 适用对象：`internal-review-copilot` / 40 正式名 `vas-internal-review`。
> 目标：把“单元测试、集成测试、端到端测试都跑完以后，人工还要审核什么才能部署”说清楚。

---

## 一、核心原则

智能审核上线不是“测试全绿即可部署”，而是“三类证据同时通过”：

1. **机器验证通过**：unit / integration / E2E 能证明本次改动在测试样本里工作正常。
2. **人工审核通过**：人工确认本次改动的业务边界、写入边界、放量范围、回退路径都可接受。
3. **上线授权明确**：部署 40、切流、生产群广播、扩大写入范围都必须被用户点名授权，授权不跨阶段、不跨会话扩张。

机器测试回答“代码能不能跑”；人工审核回答“现在敢不敢让它影响真实单据、真实群、真实审核员”。

---

## 二、上线分级

不同改动不走同一套重量级流程。先判断本次改动属于哪一级。

| 级别 | 典型改动 | 必跑验证 | 人工审核重点 | 是否可部署 40 |
|---|---|---|---|---|
| L0 文档 / 只读分析 | 文档、报告、看板口径说明 | 无代码测试；人工阅读 | 是否误导业务口径 | 不涉及 |
| L1 本地规则小改 | 白名单、场景卡、字段映射、提示文案 | 聚焦 unit / smoke | 是否扩大处理范围；是否影响写入 | 默认不可，需再过 E2E |
| L2 链路改动 | 轮询、卡片、重评、OMS 写入前置判断 | unit + integration + 可复现 E2E | 写入门禁、群通知、人群 @、失败路径 | 需人工授权 |
| L3 生产影响改动 | 40 部署、切流、enable unit、改生产群、改写入 allowlist | 全量可跑验证 + 验证报告 | 真实单闭环、熔断、回滚、放量 | 仅点名授权后可做 |

**默认保守规则**：只要会触达 40、OMS 真写入、生产业务群、现网 systemd unit、飞书 profile，就按 L3 处理。

## 三、五阶段上线流程

这套流程适配《AI 工作规范手册》的“方案-评估-执行-验证-总结”，但把阶段含义换成智能审核上线语境。

### 阶段 1：变更方案

每次上线前先写清楚：

| 项 | 必须说清 |
|---|---|
| 本次变更目标 | 例如“新增 OW01V1654 进入轮询与场景匹配”，不能只写“优化审核” |
| 影响范围 | 服务码、场景卡、OMS 字段、飞书卡片、40 unit、群聊、写入 allowlist |
| 不做什么 | 是否不点审核通过、是否不扩大生产群、是否不改其它 app/unit/secrets |
| 回退方案 | 代码回滚、40 snapshot 回滚、allowlist 收窄、停 poll/listen、恢复旧包 |

**人工审核点**：确认变更目标和影响范围有没有偷扩大。

### 阶段 2：上线评估

上线前必须把成功标准写成可判定条件：

| 评估项 | 通过标准 |
|---|---|
| 业务边界 | 本次服务码 / 场景 / 客户 / 群 / 单号范围明确 |
| 写入边界 | `OMS_WRITE_ENABLED`、`OMS_WRITE_ALLOWLIST`、待审核状态、人工 SOP 不覆盖规则明确 |
| 通知边界 | 哪些卡发群、哪些私聊、什么时候 @ 销售/客服/审核员明确 |
| 安全边界 | 凭据不进仓；不改其它项目 unit / secrets / profile |
| 回退边界 | 有 snapshot 或可回滚包；失败时知道停哪个 unit、恢复哪个路径 |

**人工审核点**：确认“风险可接受”，不是只看测试命令是否 PASS。

### 阶段 3：本机执行与节点自检

每个节点做完立即自检，不把问题攒到最后。

| 节点 | 自检问题 |
|---|---|
| 代码 / 配置改动 | 是否只改了本次相关文件；是否没有误碰凭据、`_runs/`、`logs/` |
| 白名单 / 场景卡改动 | 新增项是否只覆盖目标服务码或目标场景；旧场景是否未被覆盖 |
| OMS 写入逻辑 | 是否仍只写草稿信息；是否仍禁止 `vaOrderReview` |
| 飞书卡片逻辑 | 绿 / 橙 / 红卡出口是否符合预期；是否没有误 @ 人 |
| 40 部署包 | 是否先 snapshot；是否不包含密钥和运行态数据 |

**自检未过**：停在当前节点修，不进入集成或 E2E。

### 阶段 4：整体验证

验证要从“代码局部正确”推进到“真实链路闭环”。

| 验证层 | 证明什么 | 通过才算 |
|---|---|---|
| Unit | 单个函数 / 规则没有被改坏 | 目标断言 PASS |
| Integration | 多节点串起来能得到预期输出 | dry-run / pipeline 输出符合预期 |
| E2E 只读 | 能拉到真实候选单并完成判断 | 不写 OMS 时也能复现目标路径 |
| E2E 真写 | 指定待审核单进入 workflow、发测试群、OMS 写入草稿、人工可在 TOM 看见并修改 | 单号、群、写入字段、状态全闭环 |
| 40 冒烟 | 现网 unit active，日志正常，写 `_runs/live_poll`，未影响其它 unit | 观察窗口内无异常扩大影响 |

**关键口径**：E2E 未完成时，不能因为 unit 和 smoke 通过就部署 40。比如没有目标服务码待审核单时，应结论为“端到端验证未完成，暂不能部署”，而不是“本机测试通过即可上线”。

### 阶段 5：上线总结

部署或决定不部署后都要留记录：

| 记录项 | 内容 |
|---|---|
| 最终结论 | 可部署 / 暂不部署 / 已部署 / 已回滚 |
| 证据清单 | 测试命令、E2E 报告、人工审核结论、授权原话 |
| 影响范围 | 实际改了哪些文件、哪些 40 配置、哪些群或 allowlist |
| 遗留问题 | 例如“缺目标待审核单，未完成真写闭环” |
| 后续动作 | 等单、补测、灰度、扩大 allowlist、更新看板 |

## 四、测试通过后的人工审核清单

机器测试全部通过以后，人工至少审核以下 8 件事。

| # | 人工审核项 | 必看问题 | 红灯条件 |
|---|---|---|---|
| 1 | 变更范围 | 本次是否只解决目标服务码 / 目标场景 / 目标单号？ | 白名单、轮询范围、群范围被顺手扩大 |
| 2 | 真实写入边界 | 是否只写待审核单；是否不覆盖人工 SOP；是否不点审核通过？ | 写入不限单号、状态判断缺失、会覆盖人工内容 |
| 3 | E2E 证据 | 是否完成“真实待审核单 → workflow → 飞书 → TOM/OMS 写入”闭环？ | 没有目标单、只跑了 mock、本机 smoke 代替真写 |
| 4 | 通知与 @ 人 | 绿 / 橙 / 红卡是否发到正确位置；是否只在补信息时 @ 销售客服？ | 生产群未授权广播；误 @ 审核员/销售/客服 |
| 5 | 安全与凭据 | 包里是否无 `.env`、Cookie、日志、`_runs/`、截图？ | 凭据进仓或进部署包 |
| 6 | 40 操作边界 | 是否不改其它 unit / secrets / profile；是否先 snapshot？ | 未 snapshot 覆盖；动了其它项目配置 |
| 7 | 监控与熔断 | `MAX_PER_POLL`、`MAX_PER_HOUR`、断路/重试、日志观察是否明确？ | 放量无限制；失败后继续写 |
| 8 | 回退路径 | 谁来回滚、回滚哪个包、停哪个 unit、如何确认恢复？ | 只有“可以回滚”但没有具体动作和证据 |

人工审核结论只允许三种：

| 结论 | 含义 | 下一步 |
|---|---|---|
| 通过，可部署 | 所有必需证据齐全，风险可接受 | 等用户点名授权后执行部署 |
| 有条件通过 | 非核心缺口存在，但能通过灰度 / allowlist / 金丝雀控制 | 先按条件收窄上线 |
| 不通过，暂不部署 | 关键证据缺失或红灯条件命中 | 回到对应节点补测或修改 |

## 五、部署授权口径

智能审核项目必须把“审核通过”和“授权部署”分开。

### 5.1 人工审核通过不等于可以动 40

人工审核通过只代表：材料和风险判断可接受。

真正部署 40 还需要用户明确说出类似：

- “授权部署 40”
- “可以执行 P4 / 切流”
- “可以把这次包上到 40”
- “按这个 allowlist 做金丝雀”

不够明确的说法不能当授权：

- “看起来可以”
- “测试过了吧”
- “你处理一下”
- “先这样”

### 5.2 授权不跨阶段扩张

| 用户授权 | 允许做 | 不自动允许 |
|---|---|---|
| 授权本机测试 | 跑本机 unit / integration / E2E | 部署 40 |
| 授权部署 40 | 上传包、snapshot、重启目标 unit | 改网关、改其它 unit、扩生产群 |
| 授权金丝雀 | 指定单号 / 指定群 / 指定小时限额 | 全量待审核单 |
| 授权本次服务码 | 该服务码链路上线 | 新增其它服务码 |

## 六、准入 / 阻断 / 回退标准

### 6.1 准入条件

进入 40 部署前必须同时满足：

1. 本机相关 unit / integration / E2E 能跑的都已跑完。
2. 有验证报告，写明通过项、未通过项、未验证项。
3. 真写链路涉及的单号、群、allowlist 明确。
4. 人工审核 8 项没有红灯。
5. 已确认 snapshot 和 rollback 脚本可用。
6. 用户点名授权部署 40。

### 6.2 阻断条件

命中任一项，直接暂不部署：

- 没有目标待审核单，无法完成真写 E2E。
- `OMS_WRITE_ALLOWLIST=*` 但本轮只是验证单个新场景。
- 本次改动会覆盖人工 SOP 或可能调用审核通过接口。
- 生产群广播、@ 人范围未确认。
- 部署包含凭据、运行日志、Cookie、`_runs/`。
- 未 snapshot 就要覆盖 40。
- 需要改其它项目 unit / secrets / profile，但没有单独授权。

### 6.3 回退触发

部署后出现任一情况，优先回退或收窄：

- 非目标服务码被处理或写入。
- 非 allowlist 单号被写入。
- OMS 写入失败连续触发断路。
- 飞书生产群出现误广播或误 @。
- 40 unit 反复重启、日志异常增长、`live_poll` 状态异常。
- 审核员反馈 AI 草稿明显误导操作，且不是单例文案问题。

## 八、一句话判断法

上线前问一句：

> 如果这次部署后，系统真的开始影响真实待审核单、真实审核员和真实业务群，我们是否已经知道它会影响谁、写哪里、错了怎么停、怎么回滚？

答案不是明确的“是”，就不要部署。
