## 逐环节分析

### 1. 自主性定位

**框架说：** Agent 不是二元的"是/否"，而是从低自主性（步骤全由人定义）到高自主性（自主规划+选工具+自纠错）的光谱。关键是根据场景选择合适的自主性等级。

**我们做了什么：**
- 在立项文档里明确写了"不是聊天总结器"，是"非标增值需求采集与审核 Copilot"
- 硬性边界：Agent 禁止输出最终审核结论，禁止无确认写入 OMS
- 四路输出全部是"建议"不是"决策"：追问、转人工、补资料、SOP 草稿（待人工确认）
- 处理方式默认"暂时"，不改时效

**评价：** **做得好。** 在高风险业务场景（涉及仓库操作、客户资产）下选择低自主性是正确的。框架里的"聪明实习生"隐喻恰好对应我们的定位——AI 做预处理和建议，人工做最终判断。

---

### 2. 设计模式选择

**框架四大模式：**

| 模式 | 描述 | 我们是否采用 |
|------|------|-------------|
| Reflection | 生成→自评→改进循环 | **未采用** |
| Tool Use | 调用外部工具获取信息 | **采用**（OMS API、飞书 API） |
| Planning | LLM 自主决定步骤序列 | **未采用**（固定管线） |
| Multi-Agent | 多角色分工协作 | **架构设计了，未落地** |

**我们做了什么：**
- `Agent工作流程设计.md` 明确写了"本系统不采用 ReAct、Tree of Thoughts、Self-Refine"
- 选择了确定性链路（validate → context-bind → check-requirement → match-template → check-completeness → format-output）
- LLM 只在规则链路通过后做文本生成，不做决策
- `ruleOutputPath` 和 `outputPath` 分离，确保 LLM 不改变分流判断

**评价：** **做得好，且有充分理由。** 在试点阶段、高风险场景下，确定性链路比 ReAct 更可控可调试。但长期来看，随着场景从 1 个扩到 179 个，固定管线会不够灵活（见第 8 点）。

---

### 3. 任务分解

**框架说：** 复杂任务要拆成可独立测试的步骤（"识别工作流程步骤"）。每步有明确输入输出，便于组件级评测。

**我们做了什么：**
- 6 节点管线，每个节点独立 TypeScript 模块
- 每个节点有明确的输入类型（`AgentInput`、`ContextFacts`）和输出类型（`RequirementCheck`、`MatchResult`、`CompletenessResult`）
- 规则节点（check-requirement / match-template / check-completeness）是纯函数，可以不调 LLM 单独测
- `--skip-llm` 参数可以只跑规则不跑 LLM，用于隔离问题

**评价：** **做得好。** 这和框架推荐的"组件级评测前置"完全一致。节点边界清晰，任意一个节点改了可以单独回归。

---

### 4. 工具使用

**框架说：** 工具需要结构化定义（JSON Schema）；执行必须沙箱化；多工具编排要有状态管理；安全是首要考虑。

**我们做了什么：**
- OMS API 只读（拉单、查附件状态）
- 飞书 API 封装在 `feishu-bot.ts`（发消息、创建话题、读回复、@人）
- 附件校验基于白名单（`ATTACHMENT_BY_FILE_TYPE` 映射表），不允许自造 fieldKey
- LLM 不直接调工具——规则节点先做判断，LLM 只生成文本

**评价：** **做得好。** 工具使用范围清晰受限。不过缺少框架推荐的结构化工具 Schema 定义（我们的工具是硬编码在代码里的，不是标准 JSON Schema / MCP 格式）。

---

### 5. 评测体系

**框架说：**

> "严格的评测能力是预测一个团队能否把 Agentic 工作流做好的最强信号。"

推荐：
- **端到端评测 + 组件级评测**并行
- **客观指标**（代码可测）优先
- **LLM-as-Judge** 用于主观质量
- 评测集从小到大迭代（先 10-20 条手工，再扩大）
- **2x2 矩阵**：客观/主观 × 有无 ground truth

**我们做了什么：**
- 有评测方案文档（`Agent评测方案-V1.0.md`，6 维度 120 条规划），但**未冻结、未执行**
- 有 F-001 试点 4 条金标（P-001~P-004），业务方定义的通过线
- 有 Casebook A/B/C 对照实验设计，但**未执行**
- 16 条回归用的是规则分流对比（gate-comparison），不是对标 ground truth
- 7 条 demo 用例用的是 LLM 真实输出 + 人工看是否合理，没有标准化评分

**差距分析：**

| 框架建议 | 我们的状态 |
|----------|----------|
| 端到端评测 | 有设计（120 条），未执行 |
| 组件级评测 | match-template 有 smoke cases，其他节点没有独立评测集 |
| 客观指标 | outputPath 分流对比有，但没有 F1/Recall/Precision 等标准指标 |
| LLM-as-Judge | 没有 |
| 评测集迭代 | 从 Udesk 粗桶 → OMS 倒查 → demo 用例，方法论在演进，但每轮都没执行到出数 |

**评价：** **设计意识到位，执行严重不足。** 这是当前最大的短板——框架明确说"评测是最强预测因子"，我们有很多评测文档但 0 份正式评测报告。7 条 demo 和 16 条回归只算冒烟，不算评测。

**优化建议：**

1. **立即用 7 条 demo 出第一份正式评测报告**：对每条标注 expected outputPath + expected sceneKey + expected missingFields，计算 accuracy
2. **给 match-template 补组件级评测**：用已有的 `match-template-v0.2-smoke-cases.json` + 12 条 CASEBOOK 构造正例/反例集，计算 Top-1 Accuracy 和 Unsupported Accuracy
3. **引入 LLM-as-Judge**：对 SOP 草稿用另一个 LLM 打分（事实性 / 可执行性 / 编造率），不靠人工一条条看
4. **每轮迭代出数**：不要只写评测设计文档，每次改规则后跑一遍出数，哪怕只有 7 条也比 0 好

### 6. 错误分析

**框架说：**
- 检查失败案例的每个步骤 trace
- 建表统计每个组件的错误频率
- 按频率排序，优先修最高频错误

**我们做了什么：**
- `gate-comparison.md` 对比了规则分流变化
- `integration-report.md` 记录了 8 个集成问题并修复
- CASEBOOK 12 组 → 8 条规则：本质上是人工错误分析（"为什么这单失败→新单补了什么"）
- 但**没有系统化的错误分类表和频率统计**

**差距：** 框架推荐的是"建一张表，列出每个组件各出了几次什么错"，然后按频率排序修。我们有的是零散的案例分析和对比文档，缺少一张汇总表。

**优化建议：**

跑 183 条历史 F-001 单的完整 pipeline 后，建一张错误归因表：

```
| 节点 | 错误类型 | 频率 | 占比 | 示例单号 |
|------|----------|------|------|----------|
| check-requirement | 需求有内容但误判为不完整 | ? | ? | ? |
| match-template | F-001 单未命中 supported | ? | ? | ? |
| match-template | 非 F-001 单误命中 | ? | ? | ? |
| check-completeness | 附件已传但判为 missing | ? | ? | ? |
| generate-text | SOP 引用了不存在的字段 | ? | ? | ? |
```

然后按频率优先修。

### 7. 反思/自纠

**框架说：** Reflection 是"非常有效的性能提升技术"。生成→自评→改进循环可以显著提升输出质量。两个黄金法则：(1) 明确反思动作（检查/验证/审查）；(2) 指定具体评估标准。

**我们做了什么：** 完全没有 Reflection 机制。LLM 生成一次就输出，没有自我检查。

**当前影响：**
- SOP 草稿可能有结构不完整、操作步骤遗漏等问题，但没有自动检查
- 追问话术可能列了不该列的附件（L1 多列附件的瑕疵），没有自纠正
- `looksInvented()` 只检查单号编造，不检查逻辑合理性

**优化建议：**

这是**性价比最高的改进方向**。不需要改架构，只需要在 `generate-text.ts` 的 `generatePlain` 和 `generateSop` 后加一轮 Reflection 调用：

```
原始生成 → Reflection prompt（"检查这段输出：是否引用了输入以外的事实？是否遗漏了输入中已有的关键信息？是否包含审核通过/时效承诺等禁止表述？"）→ 如果 Reflection 发现问题则重新生成
```

成本：每条多 1 次 LLM 调用（约 +50% token）。收益：SOP 质量和追问精准度可能显著提升。建议先在 L4 SOP 生成上试 Reflection，不需要全链路加。

---

### 8. 规划能力

**框架说：** Planning 是让 LLM 自主决定步骤序列（先查什么、再做什么），分三个层次：自然语言计划 → 结构化 JSON 计划 → 代码即计划。更灵活但更难控制。

**我们做了什么：**
- 当前是固定管线，不让 LLM 决定步骤
- 但在 `Agent工作流程设计.md` 里设计了 Plan-and-Execute 架构（Planner 出任务单 → 循环执行 → Judge 三分叉），只是没有落地到 internal-review-copilot

**评价：** **当前合理。** 只有 1 个场景（F-001），固定管线够用。但当场景扩到 10+，"哪些步骤需要做、按什么顺序"会因场景不同而变化。到时候需要引入 Planning。

**何时引入：** 当 match-template 支持的场景 ≥3 个且各场景的 check-completeness 规则差异大时，就需要 LLM 参与"这条单走哪条检查链路"的决策了。

---

### 9. 多Agent协作

**框架说：** 四种通信模式——线性、层级、深层级、全对全。选择取决于任务特点。

**我们做了什么：**
- `Agent工作流程设计.md` 设计了完整的双层架构（编排层 LangGraph + 专家层 Coze DAG）
- 通信模式选的是"层级"（Supervisor + 多专家，专家不互调）
- 明确写了"不用 ReAct、不用 ToT、专家不面向用户、专家不直接通信"

- **但 internal-review-copilot 完全没有实现多 Agent**——它是单 Agent 固定管线

**评价：** **设计超前但落地滞后。** 架构文档的设计质量很高（双层职责、Judge 三分叉、Memory 形状都定义了），但当前可运行的代码是单 Agent 直线管线。设计和实现之间有代差。

**何时需要多 Agent：** 当需要"客户侧引导 + 审核侧 Copilot"同时运行，或需要动态调用不同领域专家（换标 Expert、拍照 Expert、费用 Expert）时。目前只有内部审核一个入口，单 Agent 够用。

---

### 10. 延迟与成本

**框架说：** 优先质量 → 再优化延迟 → 最后降成本。具体方法：逐步计时每个 step、识别瓶颈、并行化独立步骤、换小模型。

**我们做了什么：** 没有系统化的延迟/成本度量。

- LLM 调用有 45s 超时（`LITELLM_TIMEOUT_MS`），但没有记录每次实际耗时
- 没有每个节点的耗时统计
- 没有 LLM token 用量追踪
- 没有并行化（6 节点串行）

**优化建议：**

1. 在 `run-pipeline.ts` 的每个节点前后加 `Date.now()` 计时，写入日志
2. 在 `llm-client.ts` 的 `callChat` 返回时记录 token 用量（LiteLLM 响应里有 `usage` 字段）
3. 每日导出时统计：平均每单耗时、LLM 平均 token、最慢的单是哪条

当前 7 条 demo 的体感大概是每单 3-5 秒（规则快、LLM 慢），10 分钟轮询内处理 16 条不成问题。但上到 100+ 单/天时需要关注。

---

### 11. 安全防线

**框架说：** 主要覆盖工具执行沙箱化，提了"rm *.py"的真实事故。对 LLM 输出安全没有深入讨论。

**我们做了什么（超出框架）：**
- `looksInvented()`：主动扫描 LLM 输出，检测是否编造了输入以外的 VASC/EB/WI 单号
- `assertNoForbidden()`：硬拦"AI 已审核通过""自动通过"等禁止表述
- `generateLlmTextSafe()`：LLM 任何异常不中断管线，降级为 transfer_human
- 附件白名单：只允许 5 个 OMS 真字段名，禁止自造 fieldKey
- `confirmation_token` 设计：写入 OMS 必须带人工确认凭证（PRD 设计，未实现）
- 处理方式硬编码"暂时"，不让 LLM 改时效

**评价：** **做得好，是本项目的亮点。** 这些防线在框架里没有被系统化讨论，但在真实业务场景里至关重要。特别是 `looksInvented()` 这种"白名单校验输出事实"的做法很实用。

---

### 12. 人机协作

**框架说：** 课程主要讨论 Agent 自主能力，对人机协作模式（Human-in-the-Loop）讨论较少。

**我们做了什么（超出框架）：**
- 飞书群聊作为人机交互通道（不是 Web UI，而是业务方日常工作环境）
- 状态机管理案件生命周期（pending → assessed → awaiting_reply → reassessed → ...）
- 4 小时无回复自动催办
- 审核备注可复制粘贴到 OMS
- 每条消息末尾 💪 标记（内部识别，不暴露给被@的人）
- 去重机制（同一单同一话题不重复发）

**评价：** **做得好，是另一个亮点。** 框架讲的是"如何让 Agent 更自主"，我们解决的是"如何让 Agent 在组织流程中落地"。飞书群聊 + 状态机 + 催办这条链路，是从"技术能跑"到"业务能用"的关键桥梁。

## 优化优先级排序

综合框架建议和当前项目状态，按性价比排序：

| 优先级 | 改进项 | 预期收益 | 工作量 | 理由 |
|--------|--------|----------|--------|------|
| **P0** | 出第一份正式评测报告（7 条 demo + 16 条回归） | 有了数才能迭代 | 0.5 天 | 框架最核心的建议 |
| **P1** | SOP 生成加 Reflection 一轮 | SOP 质量可能显著提升 | 1 天 | 性价比最高的质量改进 |
| **P2** | 错误归因表（183 条跑一遍统计） | 知道该修哪个节点 | 1 天 | 框架第二核心建议 |
| **P3** | match-template 组件级评测集 | 场景扩展的基础 | 1-2 天 | 当前只有 smoke |
| **P4** | 每节点耗时 + LLM token 追踪 | 成本可控 | 0.5 天 | 简单但必要 |
| **P5** | LLM-as-Judge 对 SOP 打分 | 脱离人工主观评价 | 2 天 | 扩大评测规模的前提 |
| **P6** | L1 追问 prompt 修正（不传附件白名单） | 消除已知瑕疵 | 0.5 天 | 已知问题 |
| 长期 | Planning 引入（场景 ≥3 时） | 灵活性 | 大 | 当前不急 |
| 长期 | 多 Agent 落地 | 多入口多专家 | 大 | 当前不急 |

---

## 一句话总结

**我们在"安全防线"和"人机协作"上做得比框架建议的更好，但在"评测执行"和"Reflection"上明显落后。当前最大的 gap 不是架构设计，而是"有评测设计无评测结果"——框架说这是成功的最强预测因子，我们目前得分最低的恰好是这一项。**
