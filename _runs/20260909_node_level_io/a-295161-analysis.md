# A 边界 case 分析：VASC000000295161（为何停在 L2）

> 材料：`_runs/20260908_3scene_eval_v3/traces/VASC000000295161.trace.md`  
> OMS 场景码：20250407008（A「包裹类异常换**商品**标签上架」）  
> 实际业务（群聊）：包裹条码被涂改 → **辨认后重新打印包裹条码上架**（补贴**包裹**标）

---

## 1. Pipeline 为何停在 L2

### 输入摘要
- BEOR: `因包裹条码被涂改导致难以分辨条码扫描上架`
- RD: `辨认条码信息重新打印条码上架`
- 附件：标签文件=uploaded；EB / 多 WI 已绑定

### match-template 实际
| 项 | 值 |
|----|-----|
| hasRelabel | **false** |
| hasIdentify | **false** |
| hasShelve | true |
| hasPackageException | **false** |
| F-001 / A 分数 | 各 **1**（仅 weak:上架） |
| decision | **unsupported**（no viable candidates） |
| failureGate | match-template → transfer_human |

### 缺了什么信号？
场景卡 A 的 strong 需要：
`包裹类异常` / `包裹条码正常` / `商品条码异常` / `换商品标签`

295161 正文有的是：
- 「包裹条码被涂改」「重新打印条码」「辨认条码」「扫描上架」

**没有**「包裹条码正常 + 商品条码异常」「换商品标签」。  
「重新打印条码」也**未**映射到 hasRelabel / 「补贴包裹标签」等可计分信号（weak 里有「补贴包裹标签」，但正文写的是「重新打印条码」，字面未命中）。

### 「重新打印条码」为何没被识别？
1. 词表缺口：场景卡/打分器没有「重新打印条码 / 涂改 / 无法扫描但可读」类 strong/weak。  
2. 语义错位：即使加上「补贴包裹标签」弱信号，仍**不等于** A 定义的「换**商品**标签」。  
3. 「辨认」未触发 hasIdentify（identify 正则可能更偏「辨识」），且即便 identify=true，无 package_exception 时 A 会被 `identify_without_package_exception` 压掉（见 F-001 案例）。

**结论：** 停在 L2 对「当前三场景词表」是预期行为；问题不在 completeness，而在 **OMS 贴了 A 标签，但文本是「补包裹标」近邻场景**。

## 2. 群聊揭示的节点级应有行为

| 阶段 | 审核员实际行为 | 应对齐的 pipeline 节点 |
|------|----------------|------------------------|
| 缺异常单/商品信息 | 耿文文追问对应哪个异常单；无答复则**退回** | L1/上下文：缺 EB → 应追问或退回（本 trace 转换后已有 EB，是重提后的版本） |
| 澄清是否拆包辨识 | 「要拆包辨识吗？辨识方法要说明清楚」 | L1：若需辨识则追问方法；本单澄清为**不需要拆包** |
| 标准 vs 非标 | 先建议「入库标准增值-补贴包裹标签」；因 WB 码无法锁原包裹码 → 改走非标 | match 前/人工：标准增值可覆盖则不应进非标 L4 |
| 多 SKU | 「每个 A 包 SKU 是否同一」→ 多 SKU 时要求**辨识方法 + 包裹标签对应关系**（收辨识费） | L3/附件：对应关系类附件（本业务更像 TRPP/包裹-标签，而非换商品标） |
| 客户澄清可读 | 「涂抹无法扫描但字可看清」→ 审核接受，不再强要复杂辨识 | L1 细则：可读即「目视辨认后重打包裹标」 |
| 入库 vs 库内 | 异常在入库环节，退回错提的库内单（295986） | 场景/产品线分流，不单是 F-001/A/B |
| 新 WI 规则 | 「异常单创建的非标必须新入库单」；同 WI 退回 | completeness / 业务规则：NWEON 必须为**新** WI，且状态运输中等 |
| 附件质量 | 仓库拒收错误文件 → 重提后加急审批 | L3：标签文件存在且可用 |

群聊**最终路径**：补贴**包裹**条码上架（非标），不是「换商品标签」。  
因此：**不能把 295161 当 A 的正例金标**；适合当「OMS 错标 / 近邻场景」负例或新场景种子。

## 3. 对知识库扩展（32 场景映射）的启发

1. **拆出独立场景（建议）**  
   - 名称方向：`入库-包裹条码异常-补贴/重打包裹标签上架`  
   - 信号：涂改、无法扫描、目视可读、重新打印包裹条码、补贴包裹标签、WB 码 vs 原包裹码  
   - 负信号：商品条码异常、换商品标签、尺重辨识、拆包辨识（除非客户声明）

2. **A（20250407008）收紧定义**  
   - 必须同时出现「包裹条码正常/可用」+「商品条码异常」+「换商品标签」才高置信  
   - OMS 码不能单独命中（场景卡已写；本 case 是反面教材）

3. **标准增值闸门**  
   - 审核员先问「标准补贴包裹标签行不行」→ pipeline 应有「可标准则 transfer / 提示标准」出口，避免非标 L4 幻觉

4. **附件槽位**  
   - 「包裹和标签的对应关系」(TRPP) 在多 SKU 涂改场景被口头要求；当前 A 数据驱动必填只有 LF —— 扩展场景时应单独配置

5. **产品线**  
   - 入库非标 vs 库内非标 vs 异常单下单必须新 WI —— 属于绑定/策略层，建议进 32 场景映射的「提交约束」列，而不仅是动作关键词
