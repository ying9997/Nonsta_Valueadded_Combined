## 结论：业务方优先级链是否在数据上成立？

业务方描述：**先看异常名称+异常对象 → 定场景；匹配不到再看需求描述；§2.1 作兜底。**

| 检查项 | 结果 |
|--------|------|
| 字段是否存在 | ✓ 在 OMS 事件上存在 `eventName`/`eventObj`；✗ 不在当前 `_oms_cache` CSV |
| 异常对象是否二分 | ✓ 样本仅「包裹」「商品」 |
| 「包裹条码…」+对象包裹 → 补贴包裹标签类场景 | Top「【入库】尺重/标签辨识后换标上架」55.7% n=122 |
| 「商品条码异常」+对象商品 → 换商品标签类场景 | Top「【入库】尺重/标签辨识后换标上架」60.7% n=28 |
| 名称+对象能否唯一定场景（Top1≥90%） | 见歧义列表；部分组合成立，部分仍分散到多个 OMS 场景 |
| 全量验证 | ⚠ 未覆盖 `_oms_cache` 全量单；需按 VASC 补拉 `getEventOrders` 后再做全窗口结论 |

**综合判断（样本池）：**

1. **字段层：成立** — 审核员说的「异常名称/异常对象」对应 OMS `eventName`/`eventObj`，且对象值域符合「包裹/商品」。
2. **映射层：部分成立** — 「包裹条码异常(需客户处理)」高频，但会落到多个入库场景（含尺重换标、批量补贴包裹标签等），**不能**仅凭名称唯一映射到 §2.33；需叠加异常对象 + 需求描述/已选场景。
3. **对象层：信号弱** — 对象=包裹 / 商品 时 Top1 都是「尺重/标签辨识后换标上架」；差异主要在第二名（换商品标签 vs 拍照暂存）。不能单靠对象唯一定场景，但可作贴标对象倾向。
4. **业务方三条硬映射：本样本池均 ✗不成立**（批量异常→§2.33、商品条码异常→§2.5、A+名称→A+场景）；更可能是「应然审核规则」与「历史实操选景」不一致，或样本偏 F-001。
5. **兜底 §2.1：** 本池未验证「匹配不到→一律 §2.1」；需业务规则确认 + 对 `_oms_cache` 窗口补拉 `getEventOrders` 后再测。
