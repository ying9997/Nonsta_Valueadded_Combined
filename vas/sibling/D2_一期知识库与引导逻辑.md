# D2 一期知识库与引导逻辑

> 覆盖节点：N-M2-3（一期知识库方案）  
> 后续节点：N-M2-2 将在本文追加「路径对比」章节  
> 一期边界：异常单入口；不做实时 KB 同步；不做精确报价；不做 N-M2-5 ground truth 验收

## 1. 一期定位

模块 2 一期不是重建全量增值知识库，而是把已有静态语料整理成“异常单客户引导可用”的知识层，并与接口实时圈定层分工：

| 层级 | 权威来源 | 用途 |
|------|----------|------|
| 系统可选范围 | `pms.vasc.listAllVasc` | 判断当前异常、仓库、PSC、入口下系统实际允许客户选择哪些 VASC |
| 原子与属性 | `pms.vasc.getVascInfo` + `pms.BaseAttrRelService.findBaseAttrRelPage` | 判断服务项、互斥组、必填字段、附件、禁用原因 |
| 异常到增值语义 | `海外仓各业务环节异常类型与增值服务对照表.md` | 判断异常类型/异常编码通常对应哪些标准增值、何时非标兜底 |
| 背景解释与话术 | §2.2 本地 KB + 问问/百事通结构化答案 | 解释业务原因、客户需要提供什么、常见误选如何避免 |
| 费用 | 页面预估费用提示 + 二期价卡链路 | 一期只提示“最终以实际扣费为准”，不报价 |

一句话规则：**圈定以接口为准，语义以对照表为准，解释以静态 KB 辅助，未知走人工。**

### 2.2 问答式抽取

问问/百事通只用于补齐静态 KB 中缺的解释性知识，不能替代接口与对照表：

| 问题类型 | 示例 | 入库方式 |
|----------|------|----------|
| 标准增值适用条件 | “包裹内出现订单外商品时，客户选新单上架和直接上架的区别是什么？” | 结构化为异常编码、客户意图、推荐标准增值、所需资料、限制 |
| 非标拒绝/补全原因 | “哪些非标增值需求会被驳回？需要客户补哪些信息？” | 结构化为非标场景、必填背景、附件、转人工条件 |
| 客户话术 | “客户不确定选补贴条码还是换新条码时如何解释？” | 结构化为短话术、追问项、禁止承诺 |
| 出库/退货异常特殊口径 | “作废出库单有商品增值时应走什么处理？” | 标注为本期异常单入口解释，不扩展到普通出库下单 |

每条问答式知识必须保留来源链接或来源说明；没有来源的只能标 `pending_verification`，不能作为确定推荐。

## 3. 一期知识模型

一期不需要新建复杂实体库，可在现有 Schema 上增加一个“模块 2 推荐切片”视角：

| 实体 | 必备字段 | 来源 |
|------|----------|------|
| 异常类型 | 异常编码、异常名称、异常环节、异常对象、是否需客户处理 | 对照表、异常单接口 |
| 推荐增值 | 标准增值名称、非标兜底类型、处理说明 | 对照表、存量 KB |
| 系统候选 VASC | `vascCode/vascName/vascAttributeMap` | `listAllVasc` 实时返回 |
| 原子服务项 | `eventCode/name/vasEventDesc/mutexGroup/required/isShow/isDisable/disableReason` | `getVascInfo` |
| 属性与附件 | `attrCode/attrName/showType/pulldownValue/isRequired/fileFormat/isShow` | `BaseAttrRelService.findBaseAttrRelPage` |
| 引导话术 | 标准推荐理由、非标补全问题、转人工原因 | 对照表 + KB + 问答式抽取 |

推荐结果必须保留证据字段：

```json
{
  "exceptionEvidence": "eventCode/eventName/exceptionNode/exceptionObject",
  "semanticEvidence": "对照表章节或行",
  "systemEvidence": "listAllVasc 返回候选",
  "fieldEvidence": "getVascInfo/BaseAttrRel 返回字段",
  "kbEvidence": "KB 路径或问问来源",
  "confidence": "high | medium | low",
  "needsReview": true
}
```

## 4. 引导逻辑

### 4.1 入口判断

只在异常单链路触发：

1. 客户从异常单列表进入处理异常。
2. 第一步确认异常明细。
3. 第二步进入增值产品信息。
4. 客户点击 AI 入口，或在 α 兜底路径中输入异常单号。

非异常直接下单、普通服务中心增值申请、纯价卡咨询，不进入本引导逻辑。

### 4.2 推荐主流程

```text
异常单号/页面触发
  -> 查询异常事实
  -> 调 listAllVasc 圈定系统候选
  -> 用对照表判断标准增值语义
  -> 候选与语义交叉
  -> 标准可覆盖：推荐标准增值
  -> 标准不可覆盖：
       a) 圈定内有匹配的「命名非标原子」（≠ 入库/库内/出库其他服务需求）
          -> 直接引导选该命名增值（2a）
       b) 否则走其他服务需求（2b）
          -> 标准提问补全需求描述
          -> 对照《非标增值单审核SOP知识库-新版》相似场景
          -> 客户确认用 SOP 摘要
  -> getVascInfo/BaseAttrRel 拉必填字段与附件（2a/2b 均可能需要）
  -> 输出可回填下单的信息清单
```

**2a 例**：`包裹串仓异常调拨`（入库非标特批下与「入库其他服务需求」并列）；库内特批下代采购包材、审计盘点、DG 销毁、货权转移换标/改数。清单见 `deliverables/非标分流_命名直选_vs_其他服务需求/非标分流两类口径.md`。

### 4.3 标准增值优先规则

| 条件 | 输出 |
|------|------|
| 对照表明确异常编码/类型对应标准增值，且接口候选中存在相符 VASC | 推荐标准增值，说明原因、适用对象、下一步需填字段 |
| 对照表有标准建议，但接口候选中没有 | 不强推；提示“系统当前未圈定该标准增值”，建议人工确认或走非标 |
| 接口候选中有多个标准增值，客户意图不清 | 给 2-3 个意图选项，例如继续上架、拍照确认、销毁、自提 |
| 异常属于知悉类或无需提交增值 | 明确“无需提交增值”，只说明仓库默认处理或需知悉事项 |
| 标准增值不能覆盖客户需求 | 进入非标增值补全，不承诺一定审核通过 |

### 4.4 非标补全规则

进入非标前先判 **2a vs 2b**（详见 HANDOFF §0 与 `非标分流两类口径.md`）：

| 路径 | 条件 | AI 行为 |
|------|------|---------|
| **2a 命名直选** | 候选中有命名非标原子，且名称不是「××其他服务需求」 | 引导直接选该服务；只补该原子必填；**不要**再走长篇「其他服务需求」描述追问 |
| **2b 其他服务需求 + SOP** | 候选为入库/库内/出库其他服务需求，或意图只能落兜底 | 按模板维度标准提问 → 对照 SOP KB 相似场景 → 确认用 SOP 摘要 |

当进入 **2b** 时，AI 不直接让客户写一句“帮我处理”，而是分步收集：

| 信息组 | 必问内容 | 证据来源 |
|--------|----------|----------|
| 业务背景 | 异常单号、异常名称、客户目标、为什么标准增值不满足 | 异常事实 + 客户输入 |
| 操作对象 | 包裹/商品/单品/托盘、条码、数量、等级、是否全量处理 | 异常单货物明细 + `getVascInfo` |
| 操作动作 | 拍照、贴标、换包装、上架、销毁、自提、文件修改、其他 | 对照表 + 原子列表 |
| 字段资料 | 标签类型、尺寸规格、商品等级、文件、图片、条码对应关系等 | `BaseAttrRel`、原子可选规则 |
| 约束确认 | 禁用原因、互斥项、是否需审核、是否转人工 | `getVascInfo.isDisable/disableReason` + KB |
| SOP 匹配 | 补全后的描述与《SOP知识库-新版》场景对照 | 非标 SOP KB |

非标 **2b** 输出必须包含：

- 已收齐信息。
- 缺失信息。
- 建议上传附件。
- 相似 SOP 场景（若命中）与客户确认用摘要。
- 审核风险或转人工原因。
- 不做报价承诺。

**2a** 输出：推荐的命名原子/产品 + 短字段清单 + 关键限制（如串仓仓群）。

### 4.5 话术模板

标准推荐：

> 已根据异常编码、异常对象和系统当前可选增值范围，识别到可以优先选择「{标准增值}」。该路径比非标更标准，通常处理更快，也能减少因信息不完整被退回的概率。你还需要补充：{字段清单}。

候选不一致：

> 业务对照表里该异常通常可用「{标准增值}」处理，但当前系统接口没有圈定到这个增值产品。我不建议直接强选非标，建议先确认异常单/仓库/产品是否满足配置；如需继续处理，可按非标路径补充资料并转人工确认。

非标补全：

> 当前需求超出标准增值覆盖范围，建议走非标增值。为减少驳回，请先补充：处理对象、期望动作、条码/商品清单、附件或图片、特殊要求。费用与是否可执行以审核和实际扣费为准。

无需提交增值：

> 该异常属于知悉或仓库默认处理类，不建议为此新提交增值单。请关注异常单状态和预计销毁/处理时间；如你有额外处理诉求，再按非标路径说明需求。

## 5. 四类异常环节裁剪

| 环节 | 一期处理方式 | 边界 |
|------|--------------|------|
| 入库异常 | 重点覆盖；复用现有入库 KB 与测试集 | 只覆盖异常单入口，不覆盖普通入库增值下单 |
| 库内异常 | 覆盖对照表中的库内异常，如商品包装异常、单品条码无法扫描、错装等 | 不覆盖日常库内增值咨询 |
| 出库异常 | 覆盖对照表中的异常处理，如订单补增值后修改文件、自提出库拦截、错漏发等 | 不扩展到普通出库增值报价/下单 |
| 退货异常 | 区分知悉类、操作增值类、退货处理增值 | 知悉类不引导提交增值；无主货找回等才进入增值推荐 |

## 6. 禁区

- 不把对照表中的入库/库内/出库/退货解释为四个普通下单入口。
- 不用静态 KB 覆盖接口实时候选。
- 不根据名称相似强行匹配 VASC。
- 不输出精确报价或价差承诺。
- 不把 `expert-test-dataset-inbound.md` 当作正确答案验收集。
- 不处理 N-M2-5 的推荐命中率、错选率、驳回率量化。

## 7. 路径对比

> 节点：N-M2-2  
> 依据：N-M2-1 页面/接口核验、会议纪要、PLAN §10.2  
> 结论：一期首选 β「最小改造带主动触点」；α 仅作兜底；γ/δ 放二期。

### 7.1 路径总览

| 路径 | 定位 | 做法 | 一期建议 |
|------|------|------|----------|
| α 零改造被动窗口 | 兜底 | 复用现有在线咨询或增值专属对话框，客户主动输入异常单号/问题 | 可保留，但不作为主方案 |
| β 最小改造带主动触点 | 一期首选 | 在第二步「增值产品信息」加轻量入口，例如“不确定选哪个？AI 帮你看”；点击后智能体自取异常上下文并推荐/补全 | 推荐推进，待产品确认入口位置 |
| β2 自动打开助手侧栏 | β 变体 | 客户点击“下一步”进入第二步后，万邑联自动打开 AI 助手侧栏，并自动发送固定句式 + 异常单号，AI 直接进入推荐/追问 | 可作为 β 的更主动形态，需产品确认是否接受强制打开 |
| γ 页面感知联动 | 二期体验升级 | 万邑联前端提供操作节点 hook，AI 感知客户处于哪一步、选择了哪个增值/非标，并主动弹出 | 二期，依赖前端排期 |
| δ 前置预审核 | 二期能力 | 客户补齐信息后，AI 依据规则和接口做简单初审，提前发现缺字段、附件、明显错选 | 二期，依赖 ground truth 与审核规则 |
| D 结构化需求采集 | 本期必做 | 与 β 同一入口叠加，不新增主动触达；以 `getVascInfo` / `BaseAttrRel` 必填项 + 非标补全清单为骨架，逐项收集背景、对象、动作、字段、附件 | 一期必须纳入，目标是即使客户选错也能结构化完整提交，减少资料不全导致的审核打回 |
| E 客服 AI copilot（旁路） | 短期速上候选 | 增值单页面弹框提示客户把异常单号发给右侧 AI 客服助手，由助手输出推荐、缺失清单和非标补全建议 | 依赖开发少、上线快，适合先给业务方评审交付形态 |

### 7.1.1 本期范围补充

本期只覆盖已经进入万邑联增值单页面的客户，重点解决“进页面后不知道选哪个、选错、非标资料不完整被打回”。异常单未进入页面客户的主动触达、push、IM、邮件提醒不纳入本期范围。

### 7.1.2 D 结构化需求采集（本期必做）

D 不是独立入口，而是叠加在 β / β2 的同一 AI 入口内：客户触发 AI 后，AI 不只回答“选哪个产品”，还要把客户需求整理成审核可用的结构化信息。

机制：

- 以 `pms.vasc.getVascInfo` 返回的原子服务项、必填状态、互斥组、禁用原因为第一层骨架。
- 以 `pms.BaseAttrRelService.findBaseAttrRelPage` 返回的属性必填项、选项、附件格式为第二层骨架。
- 以非标补全清单为第三层骨架，逐项收集业务背景、操作对象、期望动作、页面字段、附件/图片/清单。
- 标准产品可覆盖时，先推荐标准增值；客户坚持非标或标准产品无法覆盖时，切入结构化补全。

价值：

- 客户即使一开始选错产品，也能按非标审核所需维度完整提交。
- 审核人员拿到的是背景、对象、动作、字段、附件齐全的需求，而不是一句自由文本。
- 降低“缺包裹范围、缺动作说明、缺附件、缺特殊要求”导致的多轮打回。
- 不承诺自动审核通过，不替代人工审核，不做精确报价。

### 7.1.3 E 客服 AI copilot（旁路短期候选）

E 用最小产品改造先把能力露出：在增值单页面弹框提示客户把异常单号发给右侧 AI 客服助手，例如“把异常单号发给 AI 客服助手，帮你判断该选标准增值还是补非标资料”。AI 客服助手按固定句式接收异常单号后，输出标准推荐、客户意图追问、非标缺失清单和提交摘要。

定位：

- 依赖开发少：只需要页面提示/弹框和既有 AI 客服助手承接，不要求页面字段级联动。
- 上线快：适合短期给业务方评审“AI 如何降低选错和打回”的真实交互形态。
- 价值有限但可验证：它仍是旁路，客户需要复制/发送异常单号，不能替代 β 的页面内主动触点。

### 7.2 六维对比

| 维度 | α 零改造被动窗口 | β 最小改造带主动触点（首选） | γ 页面感知联动 | δ 前置预审核 |
|------|------------------|------------------------------|----------------|--------------|
| 实现思路 | 在现有咨询入口或新对话框中接入增值知识库；客户主动问 | 第二步产品选择区域加按钮/浮层；AI 根据异常单号或客户上下文调用异常单查询与 VASC 接口；β2 可在进入第二步时自动打开助手并自动发送固定句式 + 单号 | 前端暴露页面步骤、已选产品、字段变化等上下文；AI 自动判断何时提示 | 在推荐和补全后，对完整需求做规则校验和简单审核建议 |
| 周期/改造量 | 最短；基本不改万邑联业务页面 | 短；按钮型只需一个入口；β2 还需页面进入第二步时触发助手打开和自动发问 | 中到长；需产品 PRD、前端 hook、状态联动、联调 | 中；需审核规则、样本、回归机制 |
| 资源依赖 | AI 侧、知识库侧 | AI 侧 + 万邑联前端入口/自动触发 + 产品确认 | AI 侧 + 万邑联产品/前端/可能后端 + Echo/孙琪协调排期 | AI 侧 + 业务审核规则 + 业务方标注数据 |
| 可解决痛点 | 能回答客户主动提出的问题；可用于客服退回后的补问 | 客户在最容易错选的第二步被提醒；按钮型尊重客户主动点击，β2 能避免客户看不到入口；可推荐标准增值、拦截非标信息不完整 | 能在客户误选、漏填、选非标时实时提示，体验最好 | 能降低审核退回率，但前提是信息已收齐且规则可信 |
| 遗留问题 | 客户不知道要问；会议纪要明确“跟现在没区别” | 按钮型仍需客户点击入口；β2 可能打扰客户，需要确认是否强制打开、是否可关闭/记忆关闭 | 排期和改造重；一期 8 月目标风险高 | 缺 ground truth；不应在一期承诺命中率 |
| 风险/卡点 | 价值不足，难证明错选率下降 | 产品是否愿意加按钮或强制打开侧栏；入口位置、触发时机和固定句式需确认 | 前端排期、PRD、联调复杂；纯外挂不可行 | 业务方正确验收集未到位，误审风险高 |

### 7.2.1 本期新增路径优劣对比

| 路径 | 最快实现程度 | 客户卡点 | 未解决痛点 | 需协调资源 |
|------|--------------|----------|------------|------------|
| α 零改造被动窗口 | 最快；可复用现有咨询入口或增值专属对话框 | 客户必须主动想到去问 AI，并且要自己输入异常单号/问题 | 不能主动拦截错选；客户不问就没有价值；难证明打回率下降 | AI/知识库侧即可，万邑联资源依赖最低 |
| β 最小改造带主动触点 | 快；第二步加入口或浮层，数据侧由 AI 自取上下文 | 客户仍需要看到并点击入口；入口位置和文案影响触发率 | 不做全页面实时感知；不自动提交；不替代审核 | 万邑联产品确认入口位置，前端加轻量入口，AI 侧接异常单查询与推荐逻辑 |
| γ 页面感知联动 | 较慢；需要前端 hook 和状态联动 | 客户体验最好，但要等页面改造排期 | 一期周期风险高；联调复杂；仍不能替代审核 | 万邑联产品/前端/可能后端，AI 侧联调，Echo/孙琪协调排期 |
| δ 前置预审核 | 较慢；依赖规则与样本，不适合当前一期承诺 | 客户需先把信息补齐，否则审核建议不可靠 | 缺 ground truth，不能承诺命中率、错选率、驳回率量化 | 业务方审核规则、正确验收集、AI 侧规则回归，不触碰 N-M2-5 前置 |
| D 结构化需求采集 | 快；与 β 同一入口叠加，不另开入口 | 客户需要按 AI 追问逐项补信息，交互比纯推荐更长 | 不能保证一定审核通过；不能解决未进入页面客户 | AI 侧补全链路，接口字段映射，业务方确认非标补全清单口径 |
| E 客服 AI copilot（旁路） | 最快之一；页面弹框提示 + 既有 AI 客服助手承接 | 客户要把异常单号发给右侧助手，仍存在复制/发送动作 | 与页面下拉框/字段无强联动；客户可能忽略弹框 | 少量万邑联前端提示资源，AI 客服助手固定句式和知识库配置 |

### 7.3 推荐路径

一期推荐 β，原因如下：

1. 触发点贴近真实错选位置：客户在第二步面对被圈定的多个增值产品时最容易迷茫，会议纪要中的痛点也集中在这里。
2. 数据侧不依赖万邑联新增接口：异常事实可由智能体既有异常单查询能力获取，VASC 候选和字段规则已有接口。
3. 改造量可控：万邑联只需给一个入口，不要求全页面感知、字段级监听或传完整上下文。
4. 可降级：如果入口暂时排不上，α 兜底仍能用同一套后端引导逻辑，客户手动给异常单号即可。

β 一期最小验收口径：

- 第二步「增值产品信息」有可发现入口。
- 触发后 AI 能识别当前异常单或要求客户补异常单号。
- 能输出标准增值推荐、非标补全清单、转人工原因。
- 不报价、不自动提交、不替代审核。

D 结构化需求采集一期验收口径：

- 与 β / β2 共用第二步 AI 入口，不新增异常单外主动触达。
- 能按背景、对象、动作、字段、附件五类输出补全清单。
- 字段与附件项可追溯到 `getVascInfo` / `BaseAttrRel` 或非标补全清单。
- 输出包含已收齐信息、缺失信息、建议附件、审核风险，不承诺通过、不报价。

E 客服 AI copilot 短期验收口径：

- 增值单页面存在可见弹框或提示，明确引导客户把异常单号发给右侧 AI 客服助手。
- AI 客服助手收到固定句式 + 异常单号后，能输出推荐、追问或非标补全清单。
- 方案标注为旁路候选，不作为最终页面联动能力承诺。

β2 自动打开侧栏验收口径：

- 客户从第一步点击“下一步”进入第二步时，AI 助手侧栏自动打开。
- 页面自动向 AI 发送固定句式 + 异常单号，例如：`请根据异常单号 {eventNo} 的当前异常情况，帮我判断应该选择哪个增值服务；如果有多个标准增值都可以，请先问我想怎么处理，再推荐合适产品；如果需要走非标，请告诉我必须补充哪些信息，避免提交后被驳回。`
- AI 不在多个标准服务均可时直接给唯一推荐，必须先追问客户处理意图。
- 客户可关闭侧栏；关闭不影响原页面保存草稿、上一步、提交等操作。

### 7.4 产品确认项

| 确认项 | 推荐答案 | 影响 |
|--------|----------|------|
| 入口放哪里 | 第二步增值产品表上方或产品选择区域旁 | 直接影响客户是否能看到 |
| 文案 | `不确定选哪个？AI 帮你看` | 避免客户以为是普通客服咨询 |
| 是否传参 | 一期不要求传完整业务参数；可选传 `eventNo` 或页面当前异常单号 | 传参越少，改造越轻；不传也可由客户输入异常单号 |
| 是否自动弹出 | 两种可选：β 按钮点击触发；β2 进入第二步后自动打开侧栏并自动发送固定句式 + 单号 | β2 更主动但可能打扰客户，需产品确认是否强制打开、是否允许记忆关闭 |
| 是否回填页面 | 一期先输出清单供客户选择/填写；回填放二期 | 避免越权和联调扩大 |

### 7.5 阶段演进

```text
α 兜底：客户手动输入异常单号
  -> β 一期：第二步增加 AI 触发入口
  -> γ 二期：页面感知客户操作，主动提示
  -> δ 二期：信息完整后自动初审简单场景
```

### 7.6 路径边界

- α 不能作为主方案向业务承诺“主动引导”，只能说可先上线能力。
- β 推荐但仍需产品确认；当前文档不假设万邑联已排期。
- γ 不能宣称零改造；PLAN 已核验 React SPA 无法靠纯外挂可靠感知页面。
- δ 不在本次 GATE 允许节点内展开验收，且 N-M2-5 ground truth 未到位。
