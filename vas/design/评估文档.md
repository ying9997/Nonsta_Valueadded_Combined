## 3. 节点成功标准与自检方法

| 节点 | 成功标准 | 自检方法 |
|------|----------|----------|
| N0 入口上下文判定 | 有 `popupContext.routeDecision = "nonstandard"` 时跳过 2d 直接进 2a/2b；无 `popupContext` 时正常触发 2d | 分别构造有/无 `popupContext` 的输入，检查 route 流程和页面初始态 |
| N1 页面上下文注入 | AI 不要求客户重复填异常单号，可读取异常编码、仓库、业务单号、当前页面已选值 | 用固定上下文模拟输入，检查 JSON 输出引用 |
| N2 候选注入 | 推荐范围只来自 `systemScopedVascList` / `listAllVasc` / `getVascInfo` | 对 `selectedVasc`、`selectedService` 做候选内校验 |
| N3 2d 标准增值纠偏 | 条件触发；`systemScopedVascList` 中 `type = "标准"` 的产品为标准增值候选；命中时明确建议客户返回标准增值路径，并给出候选内标准增值名称；不继续引导填写非标字段 | 2d 用例检查 `route`、`selectedVasc`、空字段建议；字段级校验 `type = "标准"` |
| N4 2a 命名/具体非标服务直选 | 命中当前候选内具体非标服务项，输出应选择的增值产品和服务项；不进入 SOP 追问 | 2a 用例检查 `route`、`selectedService`、`sopTemplateMatched` |
| N5 2b 其他服务需求 + SOP | 先匹配历史 SOP；有模板则最小追问并生成客户确认摘要；无模板则按 SOP 模板结构追问，不编造 SOP | 2b 有模板用例 + 无模板边界用例 |
| N6 客户确认 | 2b 确认摘要必须包含“客户确认不等于审核通过”；未确认前不生成原字段建议 | 检查对话状态和 JSON 字段 |
| N7 字段建议 | 客户确认后生成 `background`、`description` 和 `attachmentRequirements` | 检查 `fieldSuggestions` 和 `attachmentRequirements` |
| N8 前端目标态/降级态 | 目标态支持按钮填入；降级态提供可复制字段内容 | 原型和标注稿检查 |
| N9 轻量附件检查 | 如前端传附件基础元数据，输出 `attachmentCheck`；结果只提示不拦截 | 附件候选用例检查 |
| N10 评测输出 | 输出符合固定 JSON schema | JSON schema 校验；非法 JSON 判失败或兜底重试 |

## 4. 评测设计评估

### 4.1 评测集要求

评测集必须覆盖：

- 2d 标准增值纠偏。
- 2a 命名/具体非标服务直选。
- 2b 其他服务需求 + SOP。

首批规模固定为三类分支每类至少 3 条，总计不少于 9 条。每类 3 条应覆盖明确命中、信息缺失/需追问、边界/易混淆场景。

附件轻量检查进入评测设计：至少补充 3 条附件问题候选用例。附件 TOP3 问题必须先从飞书历史群聊抽取并人工确认；示例问题类型可以是单号写错、标签文件缺失、附件与需求不匹配，但不得在实地抽取前断言 TOP3，也不得写成已支持规则。

评测集构建来源：

- 来源 A：飞书历史群聊，由飞书 Aily 从审核同事与客服/销售多轮讨论中抽取候选样本，偏内部审核与业务口径真源。
- 来源 B：客服历史会话数据库，由本地 Cursor/AI IDE 或离线脚本从线上客服与客户真实沟通记录中抽取候选样本，偏客户真实表达与多轮沟通真源。

候选集来源优先级：第一阶段优先抽飞书历史群聊，第二阶段再抽客服历史会话数据库。

两类来源都只能生成候选测试集，必须经过脱敏和人工复核后才能进入金标集。若缺少 `systemScopedVascList` / `listAllVasc` 候选、`selectedService`、费用、审核结论等关键信息，不得凭空补，只能写入 `needsEnrichment` 或 `evidenceGap`。

每条用例必须包含：

- `caseId`
- 页面上下文 / 异常单上下文
- `systemScopedVascList` / `listAllVasc` 候选
- 当前页面已选值
- 客户输入
- 多轮对话历史，如有
- 期望 `route`
- 期望 `selectedVasc` / `selectedService`
- 期望 `missingFields`
- 期望 `confirmationSummary` 或字段建议
- `forbiddenOutputs`

### 4.2 输出 Schema

结构化输出 schema 是评测与中间层接口的强约束。Agent 内部/接口返回必须包含固定 JSON 字段，用于 route 判断、页面落点、字段填入、附件要求提示、轻量附件检查、状态存储、多模型评测。客户可见文案可以自由生成，但必须放在 `displayText` 字段中；客户可见文案不得替代结构化字段。若模型输出不是合法 JSON，中间层应判为失败或进入兜底重试。

```json
{
  "route": "2d_standard_redirect | 2a_named_nonstandard_direct | 2b_other_service_sop",
  "selectedVasc": {},
  "selectedService": {},
  "pageActions": [],
  "missingFields": [],
  "sopTemplateMatched": true,
  "confirmationSummary": "",
  "fieldSuggestions": {
    "background": "",
    "description": ""
  },
  "attachmentRequirements": [],
  "attachmentCheck": {
    "status": "not_checked | ok | warning | missing",
    "issues": [],
    "suggestions": []
  },
  "feeEstimatePlaceholder": "费用预估待接入",
  "displayText": "",
  "forbiddenViolations": []
}
```

### 4.3 评分维度

| 评分项 | 通过标准 |
|--------|----------|
| 路由是否正确 | `route` 等于期望分支 |
| 是否只推荐候选内产品/服务项 | 输出不得超出候选 |
| 是否正确区分 2a 与 2b | 具体非标不进 SOP 长追问；其他服务需求不冒充具体服务项 |
| 2d 是否正确返回标准增值路径 | 不生成非标字段建议 |
| 2b 是否先模板匹配再追问 | 有模板最小追问，无模板结构化追问 |
| 是否避免编造 SOP | 无模板时不得生成伪历史 SOP |
| 是否包含“客户确认不等于审核通过” | 2b 确认摘要必含 |
| 是否生成可填入原字段的建议 | 确认后生成 background / description |
| 是否输出附件要求提示 | `attachmentRequirements` 与 SOP 要求一致 |
| 是否正确执行轻量附件检查 | `attachmentCheck` 只基于附件元数据提示，不拦截提交 |
| 是否触发禁止输出 | `forbiddenViolations` 为空且人工复核无违规 |

### 4.4 多模型对比

多模型对比方式：

1. 固定同一批测试输入。
2. 固定输出 JSON schema。
3. 固定评分规则。
4. 记录每个模型的：
   - route accuracy
   - 候选内推荐准确率
   - SOP 字段完整率
   - 违规输出率
   - 人工复核备注

## 5. 风险缓解评估

| 风险 | 当前是否可接受 | 评估意见 |
|------|----------------|----------|
| AI 扩推候选外产品/服务项 | 可接受 | 必须做候选内校验；违规则转人工 |
| 2d 纠偏失败 | 可接受 | 必须有 2d 回归用例，确认不生成非标字段建议 |
| 2a/2b 混淆 | 可接受 | 必须用当前候选服务项判断；除 `包裹串仓异常调拨` 示例外，不凭空列服务项 |
| 无模板时编造 SOP | 可接受但必须硬约束 | 无模板只能按 SOP 模板结构追问 |
| 审核承诺误导 | 可接受 | 2b 摘要必须包含“客户确认不等于审核通过” |
| 前端按钮未排期 | 可接受 | 降级为文字指引 + 可复制字段内容 |
| 附件检查越界 | 可接受 | 附件检查只做提示，不做强制拦截或审核承诺 |
| 附件 TOP3 未确认 | 可接受 | 必须先从飞书历史群聊抽取并人工确认，未确认前只作为候选评测项 |
| 费用预估误导 | 可接受 | 本期只输出“费用预估待接入” |
| 视频 SOP 范围蔓延 | 可接受 | 明确为下期迭代，不纳入本期通过条件 |

## 6. 通过条件

本评估通过条件：

- 主模块明确为可独立运行的非标页内嵌方案。
- 方案已定义前置模块与主模块的关系和上线节奏。
- 三类核心分支固定为 2d、2a、2b。
- 成功标准覆盖 2d 返回标准路径、2a 具体非标直选、2b SOP 模板匹配/结构化追问。
- 前端目标态和降级态明确。
- 附件能力明确为本期轻量附件指引 + 下期复杂附件理解；本期不做复杂图片/视频解析，不强制拦截提交。
- 费用预估只占位，不实现。
- 视频 SOP 解析保留为下期迭代，不纳入本期验收。
- 结构化输出 schema 是评测与中间层接口强约束。
- 新增评测设计，支持结构化 JSON 自动评测和多模型对比。
- 首批评测集规模为三类分支每类至少 3 条，总计不少于 9 条，并追加至少 3 条附件问题候选用例。
- 下一阶段仅做 HTML 标注原型、三类分支测试集、附件候选评测、结构化输出 schema、基础评测表。
- 评测集构建方案纳入当前评测体系；真实数据抽取、脱敏和金标确认可作为下一阶段切片，不要求本期完成。
