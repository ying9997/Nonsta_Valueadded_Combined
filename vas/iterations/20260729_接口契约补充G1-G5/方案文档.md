# 方案文档 - 接口契约补充 G1-G5

> 日期：2026-07-29
> 切片：接口契约补充（G1-G5）
> 执行者：Codex
> 验收者：Opus
> 范围：在现有 `contracts/api-contract/接口契约草案.md` 和 `contracts/api-contract/字段清单_table.md` 中补充 5 个缺口字段，不改动现有已通过的字段和逻辑。

## 1. 背景

Phase 3 接口契约草案于 2026-07-28 完成，Opus 于 2026-07-29 验收核心框架通过，但识别出 5 个缺口（G1-G5）。本切片补齐这些缺口，使 Phase 4 评测切片能正确定义 input/output schema。

## 2. 缺口清单与要求

### G1: popupContext（标准页弹窗传入上下文）

**位置：** `AgentGuideRequest` 新增可选字段

**来源：** `design/方案文档.md` §2.5.3

**要求：**
- 字段名：`popupContext`
- 必填：否（缺失时 Agent 正常执行 2d 纠偏）
- 中间层负责：从前端 `GuideSubmitRequest` 透传或从弹窗会话服务获取
- Agent 消费逻辑：若 `popupContext.routeDecision === "nonstandard"`，跳过 2d，直接进入 2a/2b

**字段结构参考（来自方案文档 §2.5.3）：**
```json
{
  "popupContext": {
    "conversationId": "string, 弹窗会话 ID",
    "customerInput": "string, 弹窗中客户描述",
    "routeDecision": "string, 'nonstandard' | 'standard' | null",
    "systemScopedVascList": "array, 弹窗时的候选快照（可选，用于一致性校验）",
    "exceptionContext": "object, 弹窗采集的异常单上下文（可选）",
    "dialogHistory": "array, 弹窗多轮对话记录"
  }
}
```

**同步修改：**
- `GuideSubmitRequest` 也需新增可选 `popupContext` 字段（前端透传给中间层）
- Agent 决策流 §5 伪代码需在最前方新增 popupContext 判断分支
- 字段清单 table 两处都要补

### G2: conversationHistory（多轮对话历史）

**位置：** `AgentGuideRequest` 新增字段

**来源：** `design/方案文档.md` §3 端到端流程（2b 多轮追问）

**要求：**
- 字段名：`conversationHistory`
- 必填：否（首轮为空数组）
- 中间层负责拼接历史轮次
- Agent 用于理解多轮追问上下文

**字段结构：**
```json
{
  "conversationHistory": [
    {
      "turnId": "string",
      "role": "string, 'user' | 'agent'",
      "content": "string, 该轮用户输入或 Agent customerMessage",
      "timestamp": "string, ISO 8601",
      "route": "string, 该轮 Agent 输出的 route（仅 role=agent 时）",
      "matchState": "string, 该轮匹配状态（仅 role=agent 时）"
    }
  ]
}
```

### G3: confirmationSummary（客户确认摘要）

**位置：** `AgentGuideResult` 新增字段

**来源：** `design/方案文档.md` §3 Step 5b + §6 输出结构

**要求：**
- 字段名：`confirmationSummary`
- 必填：条件必填（route=2b_other_service_sop 且 matchState=matched 时必填）
- 必须包含"客户确认不等于审核通过"固定句式
- 其他分支（2d, 2a）为空字符串或 null

**同步修改：**
- `GuideSubmitResponse` 也需透传此字段
- 字段清单 table 两处补

### G4: missingFields（追问清单）

**位置：** `AgentGuideResult` 新增字段

**来源：** `design/方案文档.md` §4 决策树 Step 6 + §6 输出结构

**要求：**
- 字段名：`missingFields`
- 必填：是（无追问时为空数组）
- 用于 2b 信息不足时告知前端"还缺什么"

**字段结构：**
```json
{
  "missingFields": [
    {
      "fieldKey": "string, 标识缺失的信息类型",
      "displayLabel": "string, 前端展示的追问文案",
      "priority": "string, 'required' | 'recommended'",
      "relatedSopSection": "string, 对应 SOP 模板哪个章节（可选）"
    }
  ]
}
```

**与 pageActions 的关系：**
- `missingFields` 非空时，Agent 应同时输出 `pageActions` 含 `ask_followup` action
- `missingFields` 为空 + matchState=matched 时，Agent 才输出 `fill_field` action

### G5: sopContext（SOP 模板注入）

**位置：** `AgentGuideRequest` 新增可选字段

**来源：** `design/方案文档.md` §4 Step 5a

**要求：**
- 字段名：`sopContext`
- 必填：否（2d/2a 不需要；2b 且模板库超 token 限时由中间层注入）
- 两种模式：
  - `injectionMode = "prompt_embedded"`: 模板全文已嵌入 system prompt，本字段可为空
  - `injectionMode = "middleware_filtered"`: 中间层预过滤后注入 top-N 匹配模板

**字段结构：**
```json
{
  "sopContext": {
    "injectionMode": "string, 'prompt_embedded' | 'middleware_filtered'",
    "filteredTemplates": [
      {
        "templateId": "string",
        "title": "string",
        "matchScore": "number, 0-1",
        "templateContent": "string, 模板全文或摘要"
      }
    ],
    "totalTemplateCount": "number, 模板库总数",
    "tokenBudgetExceeded": "boolean, 是否因 token 限制而走预过滤"
  }
}
```

## 3. 执行规范

1. **只改两个文件：** `contracts/api-contract/接口契约草案.md` 和 `contracts/api-contract/字段清单_table.md`
2. **不改现有字段：** 已有的 schema 结构、枚举值、阈值规则保持不变
3. **新增字段插入位置：**
   - G1 popupContext: 插在 `AgentGuideRequest` 的 `sessionState` 之后
   - G2 conversationHistory: 插在 `AgentGuideRequest` 的 `userInput` 之后
   - G3 confirmationSummary: 插在 `AgentGuideResult` 的 `fieldSuggestions` 之后
   - G4 missingFields: 插在 `AgentGuideResult` 的 `confirmationSummary` 之后
   - G5 sopContext: 插在 `AgentGuideRequest` 的 `candidateSnapshot` 之后
4. **Agent 决策流更新：** §5 伪代码开头加 popupContext 判断；§5 输出阶段加 confirmationSummary 和 missingFields 逻辑
5. **字段清单同步：** 每新增一个字段，字段清单 table 的对应 section 必须同步更新
