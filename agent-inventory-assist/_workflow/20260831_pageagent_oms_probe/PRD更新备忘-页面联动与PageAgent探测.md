## 1. 一句话结论（建议写进 PRD 概述或 §6.5 开场）

客户确认后的页面联动，**主通道必须是结构化动作（`fieldKey` + 白名单）→ 前端映射 → 按控件执行 → 用页面回读验收**。  
**禁止**把侧栏/Coze 的自然语言直接交给页面执行器（如 PageAgent `execute('选择上架')`）去点表单。  
**禁止**页面执行器点「提交 / 保存草稿 / 上一步」等收尾按钮。

本次在 demo 上验证：编号/映射通道两轮四点全对；人话含糊时两轮都点错卡片，未拉黑时还会自己提交。

| PRD 现有说法 | 探测结果 | 建议 |

## 3. 建议补进 PRD 的条款（可直接改写进 §6.5 / §5.0）

### 3.1 执行器选型（建议新增小节，挂在 §6.5 下）

页面联动允许使用第三方页面执行器（本次评估：alibaba/page-agent）。约束：

1. Coze / Expert **只输出**现有 `uiActionProposal.actions`（`type` + `fieldKey` + `valueCode` / `value`）。不输出 CSS selector，不输出「去点某某」人话给执行器。
2. **前端持有** `fieldKey → 页面定位` 映射（选择器或等价稳定锚点）。定位后若执行器只认内部编号，由前端翻译成编号再调用。本次实测：PageAgent **不接受** `{action, selector}`，只接受 `clickElement(index)` / `inputText(index, text)`。
3. 官方 Demo 里的 `{type:'type', targetId:'element-x'}` **不是**可用公开 API，PRD 不要按截图格式写死。
4. 人话 `execute(一段中文)` 仅可用于内部探测对照，**不得**作为 V1.0 对客回填主通道。

### 3.2 建议补一句到 §5.2 `uiActionProposal.actions`

保持现有 `fieldKey`，并加注释：

> `fieldKey` 必须能在前端白名单映射表中解析到当前页可见控件。映射表由前端维护，不随 Coze 输出下发 CSS。执行器若使用内部编号，编号只在当次 `updateTree`（或等价索引）内有效，下一步动作前必须重新索引并再次回读。

### 3.3 动作黑名单（建议写入 §6.5「前端执行约束」）

下列控件**永远不进入**页面执行器的可交互名单（PageAgent：`interactiveBlacklist` / `data-page-agent-not-interactive`）：

- 提交
- 保存草稿
- 上一步
- 以及任何会写单据、关单、离开编辑的按钮

依据：未拉黑时，人话「选择上架」两轮都点了提交并出现「增值单提交成功」。拉黑后两遍人话均 `是否提交=否`；执行器仍可能改打「保存草稿」主意，故收尾按钮应整组拉黑，不能只挡提交。

单据写入仍走 PRD 节点 5：客户点提交 → 前端校验 → 后端 Skill。

### 3.4 成功/失败判定（建议写入节点 4 评测口径与 §6.5）

每步动作之后必须 `pageReadback`，规则：

| 情况 | 判定 | 对客/侧栏 | 后续 `actions` |
|---|---|---|---|
| 目标控件不存在或不可见（含仅在隐藏 DOM 里能 query 到） | 失败 | 「还没有这个字段，请先完成上一步」 | **中断** |
| 映射表解析不到 `fieldKey` | 失败 | 「找不到这个字段，请核对配置」 | **中断** |
| 执行器返回失败（如编号无效） | 失败 | 「控件已过期，已停止自动填写」 | **中断** |
| 执行器返回成功，但回读值 ≠ 提案值 | 失败 | 「没有选中/填入预期内容，实际是××」 | **中断** |
| 回读值 = 提案值 | 成功 | 可进入下一步 | 继续 |

**禁止**用执行器返回的 `success` / 自然语言 `data` 当作任务成功（与 PRD §2「不以大模型输出文本作为成功依据」一致）。

选择器命中隐藏残留节点不算可执行（探测 E-2）。

### 3.5 与现有白名单动作的对应（建议补进 §6.5 表下）

本次 demo 可执行、且与 PRD `select` / `fill` 对齐的目标：

| `fieldKey`（建议名，产品可改） | 动作 | 验收 |
|---|---|---|
| 处理方式 / method | `select` → 「原单上架」 | 对应卡片 `.selected` |
| 增值服务 / service | `select` → 「入库其他服务需求」 | 对应卡片 `.selected` |
| `requirementBackground` | `fill` → 提案文本 | textarea 值为提案文本 |
| `requirementDescription` | `fill` → 提案文本 | textarea 值为提案文本 |

顺序：先 `select` 处理方式，再 `select` 增值服务，再 `fill` 两框。服务未选出时两框不在 DOM 上，强行 fill 必须按 §3.4 中断。

`show_attachment_requirement`、附件实际上传：本次未测。

## 4. 人话通道为什么不能当主路径（建议写入风险或 §6.5 反例）

同一夹具、相同人话，第 1、2 轮及拉黑后第 3 轮（人话两遍）结果一致：

| 说法 | 结果 |
|---|---|
| 写清四步（原单上架 + 入库其他服务需求 + 探针背景 + 探针描述） | 能填对 |
| 「选择上架」 | 点成增值服务「直接上架」（页上还有处理方式「原单上架」） |
| 「选择入库」 | 点成「入库-补贴包裹条码」，不是「入库其他服务需求」 |
| 「选择上架」且提交未拉黑 | 额外自动提交 |

人话不稳定、会超授权。结构化 `fieldKey` 在冲突近义词下仍点对（N-4：`clickElement` 仍是「原单上架」）。
