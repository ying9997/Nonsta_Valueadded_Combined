## 1. 你的业务逻辑，对照需求后怎么理解

你要的不是「随便出一张卡」，而是这一串：

1. 专家根据异常 / 客户意图，从 PlanEvent 接口里已启用的方案里挑：**增值产品（vascCode）+ 处理方式 + 原子列表（atomCodes）**。
2. 侧栏出一张卡，让客户看懂并点确认（PRD 硬性：未确认不得回填、不得提交）。
3. 确认后，前端把**这一组**在当前 EDS 页选中：产品、服务原子、以及方案明细里绑在一起的组合项。
4. Agent 不直接点浏览器，也不自动提交审核。

这和 PRD 已经写死的责任拆分是同一件事：

| PRD 节点 | 谁做 | 对应你这句话 |
|---|---|---|
| 页面状态采集 `pageContext` | 前端 | 当前页有哪些可选产品/服务（不是整页 HTML） |
| 结构化建议 + `uiActionProposal` | Expert / Planner | 推荐哪几个原子、确认后要选哪些字段 |
| 页面联动执行 | 前端，客户确认之后 | 选中原子和相关组合 |
| 提交写入 | 后端，要 confirmation_token | 本期先不谈提交 |

PlanEvent 接口给的是**业务组合清单**（哪个异常允许哪些 VASC + 原子），不是 DOM 第几个按钮。前端选中时，应对 `vascCode` / `atomCode` 这类业务键，而不是 `clickElement(0)`。

现有出卡样例 `fixtures/sidecar-render-a2ui.json` 点的是「第 0 个可点元素」，只够证明管道通，**不够实现「按方案明细选中一组原子」**。

## 2. 通道方案对照（针对「推荐完再出卡再选中」）

| | 甲：副本 Query 出口带回 sidecar，Bot Client 三格转发插件 | 乙：三格挪进 Query、A1 后面 | 丙：标识跟在气泡里，前端从聊天拆 | 丁：专家里发插件或读 DOM |
|---|---|---|---|---|
| 和现网分层 | 对话流仍只负责发令；Query 补上「专家决定出什么卡」。和现网「Query 问答、Bot Client 包一层」一致 | 把发令塞进现网最重的问答画布 | 现网气泡只给人看；机器包要活过 A1 | 专家层没有会话 id、没有浏览器 |
| 和 PRD | 人话走 A1；`uiActionProposal` 走 sidecar 原样到前端。最贴 `requiresUserConfirm` | 也能带包，但 Query 更难隔离 | 人话和机器包挤在一句里，A1 会改写 | 违反 PRD「Agent 不直接操作页面」 |
| 客户点确认后选原子 | 卡上按钮带业务键（fieldKey + vascCode/atomCode），前端执行白名单 select | 同左，但改点在 Query | 若标识被吃掉，前端拿不到要选谁 | 做不到稳定选中组合 |
| 隔离现网 | 只改副本 Query F_1 的结束/会话变量；现网 staging_D 不动 | 必须改副本 Query 内部主线，冲突面大 | 可不改 Query，但专家输出仍过共享 recaller/A1 | 动专家即可，业务上错层 |
| 优点 | 插件通道前端已按 `queryToolCall` 做；人话与选中数据分开；普通问答不误发 | 代码能直接看见 A1/专家文本，少一跳 | 前端少改发消息方式 | 看起来改得少 |
| 缺点 | 要改副本 Query 出口（需你点名）；Chat API 看不到插件，要用调试页或侧栏验 | Query 节点极多，和「正在思考」插件挤在一起 | 标识过 recaller 总结和 A1 大概率没；气泡可能闪 JSON | 专家看不见页，也发不出带会话的 tool_call_send |
| 对你这句需求 | **能承载**：推荐原子 → 卡确认 → 按 PlanEvent 组合选中 | 能承载，但不是最小改动 | **难承载**：机器包活不到气泡 | 不承载 |

**结论：继续走甲。** 乙是甲的换位置，不是更贴业务。丙适合「前端坚持解析聊天」且第 0 步证明标识还在——今天的探测显示气泡里没有标识。丁排除。

甲要补的不是再加节点，而是两件事：

1. 副本 Query 把专家 `structured`（或单独 sidecar）**原样**交到 Bot Client，人话仍走 A1。
2. sidecar 里的动作从「点第 0 个元素」改成 PRD 的 `uiActionProposal`（`select` + `fieldKey` + `valueCode`），值来自 PlanEvent 的 `vascCode` / `atomCodes`。前端 catalog 若还只有 `clickElement`，要和前端对齐：用业务键选中，还是先 pageRead 再按选项文本 `selectOption`。

## 4. 和「直接探测出对比报告」的边界

**现在能对比的：**

- 发令管道（三格 / smoke）是通的。
- 推荐问句已经能出人话，但人话里没有机器包 → 丙以当前 Bot 实测为负。
- Chat API 看不到插件 → 甲的「卡有没有发出去」不能用聊天记录当证据。

**现在不能对比的：**

- 甲 vs 乙的端到端（都还没改 Query）。
- 「确认后选中一组原子」——前端 catalog 仍是 DOM 操作，PRD 是业务字段键，PlanEvent 还没接到 expert 输出。

所以本报告是：**管道探测 + 需求对照 + 缺口清单**，不是甲乙丙三条都在 EDS 页跑完的 A/B 实验。
