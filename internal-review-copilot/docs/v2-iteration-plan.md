## 一、补齐 43 张场景卡的 requiredInfoFields

### 目标

当前 75 张场景卡中 32 张有 `requiredInfoFields`（L2.5 能精准追问），43 张没有（L2.5 跳过信息检查直接放行）。补齐后所有场景都能精准追问。

### 现状

| 步骤 | 状态 |
|------|------|
| G-1 提炼脚本（extract-scene-requirement-fields.ts） | ✅ 写好了 |
| G-1 跑了 38 个场景 | ✅ 产出在 `_runs/20260914_scene_requirement_fields/` |
| G-1b 模糊匹配 OMS 码脚本（fuzzy-match-oms-codes.ts） | ✅ 写好了 |
| G-1b 跑模糊匹配 | ❌ 脚本写了没跑 |
| 写入场景卡（apply-requirement-fields.ts） | ✅ 已跑，写入了 32 张 |

### 做法

```
Step 1：跑 G-1b 模糊匹配
  → fuzzy-match-oms-codes.ts 给 43 张无码卡找 OMS 码
  → 预计 15-25 张能匹配上
  → 产出匹配报告，人工确认

Step 2：确认后补码到场景卡
  → 把匹配上的 OMS 码写入 omsSceneCode

Step 3：重跑 G-1 提炼
  → 对新补码的场景跑 extract-scene-requirement-fields.ts
  → 产出 requiredInfoFields

Step 4：写入场景卡
  → apply-requirement-fields.ts 补充写入

Step 5：剩余匹配不上的（预计 15-20 张）
  → 没有历史数据，手动写 requiredInfoFields
  → 或等这些场景线上跑出数据后再补
```

### 验证

- 跑完后统计：75 张卡中有 requiredInfoFields 的比例（目标 ≥ 50 张）
- 用之前 E2E 的 5 条待审核单重跑，看 L2.5 追问是否变化

### 预计工作量

Step 1-4：0.5 天（脚本都有，跑一下就行）
Step 5：看情况，可以后补

## 二、场景匹配准确率提升 + 验证

### 目标

用已有的测试集（golden labels + 历史跑批），对比增强前后的场景匹配准确率。增强手段：requiredInfoFields 补齐 + RAG 案例库 + 其他。

### 验证方案

**用同一批测试数据跑 A/B 对比：**

| 配置 | 场景卡 | requiredInfoFields | RAG | 对比什么 |
|------|--------|-------------------|-----|---------|
| 基线（当前） | 75 张 | 32 张有 | 关 | — |
| 增强 A | 75 张 | 50+ 张有 | 关 | requiredInfoFields 补齐的独立贡献 |
| 增强 B | 75 张 | 32 张有 | 开 | RAG 的独立贡献 |
| 增强 C | 75 张 | 50+ 张有 | 开 | 两者叠加 |

**测试数据：**

| 数据集 | 条数 | 用途 |
|--------|------|------|
| t14-golden.jsonl | 5 条 | 精准评测（有 expectedScene） |
| 历史跑批试点 20 条 | 20 条 | 覆盖度评测（有 OMS 审核员实际选的场景） |
| 40 线上跑的真实单（从 case-store 取） | 若干 | 真实场景分布评测 |

**指标：**

| 指标 | 含义 |
|------|------|
| 场景精准匹配率 | AI 判的 = 审核员选的 |
| 场景可接受匹配率 | AI 判的在 acceptableScenes 内 |
| L2 转人工率 | 转人工的单占比（越低越好，说明 AI 能处理更多） |
| L2.5 追问率 | 需要追问信息的单占比（不是越低越好——该追问的要追问） |
| L4 到达率 | 能走到 SOP 生成的单占比 |

**跑评测用现有脚本：** `run-objective-eval.ts`（精准评测）+ `run-historical-batch.ts`（覆盖度评测）

### 做法

```
Step 1：跑基线（当前配置）
  → 用 5 条 golden + 20 条历史 → 记录指标

Step 2：补齐 requiredInfoFields（一、的产出）
  → 重跑同一批数据 → 对比指标（增强 A）

Step 3：开 RAG（RAG_ENABLED=1）
  → 在增强 A 的基础上开 RAG → 对比指标（增强 C）
  → 也单独跑只开 RAG 不补卡的（增强 B）

Step 4：汇总对比报告
```

### 预计工作量

Step 1-3：各 0.5 小时（跑脚本等结果）
Step 4：0.5 天（分析 + 写报告）

## 三、RAG 案例库优化

### 当前状态

- 入库案例库：105 条（inbound-cases.jsonl）
- 库内案例库：122 KB（instock-cases.jsonl）
- BM25 内存检索，阈值 ≥ 1.0 才注入 prompt
- 默认关（RAG_ENABLED=0）

### 已验证结论

2026-09-15 B 类 6 条试跑：BM25 RAG 开了反而把 1 条判对的带错（326295 被相似案例带去换商品标签）。其余 5 条无变化。**BM25 关键词检索召回不准是主因**——"补贴""标签""上架"在多场景重叠，BM25 按词频召回了错场景的案例。

### 做法（更新）

```
Step 1：诊断 BM25 召回质量
  → 对 B 类 6 条单，看 BM25 top 3 召回的是什么案例
  → 统计：召回的案例场景对不对

Step 2：如果召回场景不对（已确认）
  → 换 embedding 向量检索（参考 complaint-intelligence-system 的 FAISS + Sentence-Transformers）
  → 按语义相似度召回，不靠关键词重叠
  → 重跑 B 类 6 条对比

Step 3：如果 embedding 召回准了
  → 加 reranker（CrossEncoder）二次排序
  → 全量评测对比

Step 4：确认有提升后
  → RAG_ENABLED=1 默认开
```

### 依赖

需要 embedding 服务（LiteLLM 端点是否支持 embedding API？或单独部署 Sentence-Transformers）。

### 依赖

依赖二、的评测结果。

## 四、群聊关联的追问链路端到端验证

### 目标

V1 只验证了"信息够的单不被误拦"。V2 需要验证"信息不够的单 → 追问 → 补信息 → 走到 L4"的完整链路。

### 做法

```
Step 1：从历史增值单里找"被打回重新提交"的 case
  → 通过 EB 号关联：同一个 EB 下有多个 VASC（第一次被退回，第二次通过）
  → 第一次的需求描述 = "不完整版"，第二次 = "完整版"
  → 群聊里有审核员要求补充的记录

Step 2：用第一次的需求跑 pipeline → 预期停在 L2.5 追问
Step 3：模拟补充（用第二次的需求或群聊里的补充信息）→ 重跑 → 预期到 L4
Step 4：在飞书测试群展示完整的多轮交互
```

### 依赖

需要群聊数据（三群合并版）+ OMS traces 表（被退回的记录）。

### 预计工作量

1 天。

## 五、场景卡质量修复（3 个已知问题）

### 问题 1：附件必填规则样本太少

当前附件规则来自早期 `attachment-analysis.md`，部分场景只有 5 条样本。如 `inbound-package-exception-relabel-shelving` 的 "标签文件必填"基于 5 条样本 100% 出现率，但真实单 VASC000000368355 上传了"对应关系表"没传"标签文件"，被误拦。

**做法：** 用 G-1 同样的大样本量（每场景 10-20 条）重跑附件出现率统计，更新 `requiredFieldKeys`。脚本参考 `scripts/batch-attachment-stats.ts`。

### 问题 2：L2.5 不看附件内容判"信息缺失"

"商品标签数量" 在附件（对应关系 Excel）里有，但 L2.5 的 LLM 只看需求描述文本 → 判"未说明"。

**短期修法：** L2.5 的 LLM prompt 加一句："如果客户上传了相关附件（如对应关系表、操作说明），附件中可能已包含数量、对应关系等信息。已上传附件时，不要将这些信息判为缺失。"

**中期修法：** V3 附件内容进 LLM。

### 问题 3：场景卡 boundaryRules 旧版命名

75 张场景卡的 `boundaryRules` 和 evidence 文件里大量使用 F-001/A/B 旧名。需要统一替换为 OMS 全名。

**做法：** 批量脚本扫描 75 张卡 + evidence 文件，把 F-001 → 【入库】尺重/标签辨识后换标上架，A → 【入库】包裹类异常换商品标签上架，B → 【入库】指定商品拍照暂存。同时检查 boundaryRules 里引用的场景是否都在当前 75 张卡里。

**预计工作量：** 3 个问题合计 1 天。
