# 状态机三版本路线图（v2）

> 结合用户反馈更新。V1 = 上线必须，V2 = 上线后尽快迭代，V3 = 资源允许再加。
> 
> 约定：L1=需求完整性校验，L2=场景匹配，L3=场景必填字段和附件校验，L4=场景 SOP 生成。
> clarification_sent 是 @销售/客服 让他们补充客户需求，不是直接追问客户。
> 场景卡 = 场景注册，分批注册上线，按 `scene-rollout-playbook.md` 流程走。

### V1 的"转人工"边界

转人工 = **agent 链路终止，审核员接手在 OMS 页面操作**。具体边界：

| 场景 | agent 做什么 | 审核员做什么 |
|------|-------------|-----------|
| L2 选"人工处理" | 发转人工消息 + 摘要 | 在 OMS 手动选场景、写 SOP、审核 |
| SOP 修改 3 次仍不满意 | 自动转人工 | 在 OMS 手动编辑 SOP |
| pipeline 异常/LLM 失败 | 降级为 transfer_human | 在 OMS 手动处理 |

**V1 不支持：agent 链路内编辑场景/SOP 后再回到 pipeline。** 审核员要么接受 AI 的结果写入 OMS，要么转人工自己在 OMS 改。SOP 修改闭环是唯一的"人机迭代"入口。

### V1 上线阻断项

| 缺的 | 工作量 | 阻断级别 |
|------|--------|---------|
| SOP 修改闭环 | 已落地 | 常驻 listen + 流式改写 + 确认后写 OMS；E2E 本轮打通 |
| OMS 写入失败重试 | 0.5 天 | 阻断（失败后无法恢复） |
| sop_ready 从 TERMINAL 移除 | 0.5 小时 | 阻断（否则卡片按钮不响应） |

## V2 — 上线后第一周迭代

**原则：人工可以覆盖 AI 的任何判断 + 附件链路打通 + 每次人工操作记录 badcase。**

```
                              ┌──────────────────────────────────────┐
                              │    V2 在 V1 基础上新增（★ 标注）      │
                              └──────────────────────────────────────┘

V1 状态机保持不变，新增以下链路：

★ 链路 A：人工覆盖场景（飞书卡片已有按钮支持）
  任何状态 → 审核员在话题回复指令：
    "强制场景：包裹条码批量异常"
    → parse 指令 → 覆盖 matchResult.sceneKey
    → 用新场景重跑 L3→L4
    → 记录 badcase：{AI判的, 人工改成的, 需求原文}

★ 链路 B：人工覆盖附件判断
  sop_ready 或 L3 → 审核员在话题回复：
    "强制缺附件：标签文件"
    → 覆盖 check-completeness → 回到 L3 → @销售补附件
    "强制通过附件"
    → 跳过 L3 → 直接到 L4
    → 记录 badcase

★ 链路 C：附件补齐闭环
  L3 @销售补附件后：
    → 销售/客服在飞书话题上传文件
    → agent 接收飞书文件 → 通过 TOM API 上传到 OMS 附件槽
    → 重新读取 OMS 附件状态
    → 只重跑 L3→L4（场景不变，不从头跑）
    → 齐了 → L4
    → 还缺 → 继续 L3
  两个前置探测：
    ① agent 能否接收飞书话题里上传的文件（飞书消息 API）
    ② TOM Cookie 能否上传到 OMS 附件槽（任务 C 在探测中）

★ 链路 D：L3 精准回退（不从头跑）
  附件补齐后或人工覆盖后：
    场景没变 → 只重跑 L3→L4（跳过 L1 和 L2）
    场景变了 → 从 L2 重跑（跳过 L1）
    需求描述变了 → 从头重跑 L1→L2→L3→L4

★ 链路 E：badcase 数据回流
  所有人工覆盖操作自动记录：
    → _runs/{date}_badcase/badcase-log.jsonl
    → 定期分析 → 指导 match-template 信号词扩展 / SOP prompt 优化
```

## V3 — 锦上添花（人工可兜底）

**原则：有了更好，没有不影响核心功能。**

```

  人工兜底：审核员看附件手动确认 SOP 内容

  定期查 OMS 订单状态：
    审核员直接在 OMS 审核通过了 → case-store 同步为 written_back
```

## 总结对比

| | V1 上线必须 | V2 第一周迭代 | V3 按需排期 |
|---|---|---|---|
| 新增状态 | `sop_editing` | 无（用指令覆盖，不加新状态） | 无 |
| 核心链路 | L1→L4 + 场景确认 + SOP 修改 + OMS 写入 | +人工覆盖 + 附件闭环 + 精准回退 | +附件进LLM + OMS 同步 + 配置表 |
| 人机边界 | AI 处理或转人工（二选一） | 人工可覆盖 AI 任何判断 | AI 能力增强，人工操作更少 |
| badcase | 无 | 每次人工覆盖自动记录 | +持续评测监控 |
| 附件 | 只查状态（uploaded/missing） | +飞书→OMS 上传 | +附件内容进 LLM |
| 工作量 | SOP 修改 1.5 天 + 写入重试 0.5 天 = **2 天** | **3.5 天** | 每项 0.5-3 天 |
| 上线阻断 | **缺了不能上** | 缺了能上但体验差 | 缺了不影响，人工兜底 |
