一眼结论

这套链路是一个“规则编排 + 场景卡知识 + LLM 辅助判断/生成 + 人工审核出口”的工作流。 规则负责入口约束、字段绑定、候选召回、附件/SKU/写入门禁；LLM 主要用在四处： 场景分类 refine、场景级必填信息语义判断、追问/转人工话术、SOP 生成与反思检查。

正式轮询里首判默认开启 sceneLlm=true、sceneLlmVersion=2，但 RAG 默认关闭。 所以当前 badcase 最重要的拆法是：先看退出节点，再看是规则拦截、LLM 分类、L2.5 语义完整性、 SOP 生成，还是 OMS/飞书出口问题。

规则和 AI 怎么分工

规则负责“能不能走”和“事实边界”

  • 入口合法性、服务原子过滤、字段/附件/单号抽取。
  • 需求是否空白/过短的 L1 兜底。
  • 场景卡候选召回、negativeSignals、动作约束。
  • 附件是否上传、WI 是否绑定、SKU 一致性、T1 单/多 SKU。
  • OMS 写入门禁：待审核、人工 SOP 不覆盖、allowlist、dry-run。

AI 负责“语义判断”和“文本生成”

  • 在规则候选内判断最终场景，而不是自由发挥全量检索。
  • 判断场景必填信息是否已在原文、附件线索、OMS 已知事实中出现。
  • 生成追问、转人工、回复总结、SOP 草稿。
  • 用反思 prompt 检查 SOP 是否编造、遗漏、越界；失败时尽量重写或降级。

LLM 节点与提示词

LLM 节点触发条件提示词来源输出备注
场景分类 v1/v2/v3 runPipeline({ sceneLlm: true })；正式首判是 v2。 代码内动态 prompt：buildSystemPromptV1/V2/V3、buildUserMessageV1/V2/V3。 matchedScene, topicSummary, confidence, reasoning, ambiguous。 v2 加异常单详情和 A/B/C/D 规则；v3 是 tool calling 实验版，可调用异常单、入库单、场景定义工具。
L2.5 信息完整性 场景已匹配且 skipInfoLlm=false，并且场景卡有 requiredInfoFields。 代码内动态 prompt：buildInfoPrompt。 checks[] 和 missing[] JSON。 附件不让 LLM 判；附件规则来自 checkCompleteness。
需求追问 outputPath=needs_requirement_clarification。 prompts/requirement-clarification.md + rule result factBlob。 发客服/销售的中文追问。 不能补事实、不能生成 SOP。
资料追问 outputPath=needs_field_clarification。 prompts/field-clarification.md + rule result factBlob。 场景化补资料话术。 一次说完信息和附件，不拆两轮。
转人工理由 outputPath=transfer_human。 prompts/transfer-human.md + rule result factBlob。 给审核员看的 1-3 句理由。 只复述规则结论，不生成 SOP。
SOP 生成 outputPath=sop_generated。 prompts/sop-generate.md + SOP KB + 动态约束块。 requirementDescription, requirementBackground, warehouseSop, sopText, 单号提取。 JSON mode；失败会二次要求合法 JSON；编造单号会重试或替换为 [待补充]。
SOP 反思 SOP 首版生成后。 prompts/sop-reflection.md。 PASS 或问题 JSON。 发现问题会带约束再生成一次；反思失败不阻断原流程。
回复总结 飞书话题收到人工补充后。 prompts/summarize-reply.md。 可复制进 OMS 备注的结构化文本。 若 LLM 失败，有代码 fallback 模板。

代码内动态 Prompt 摘要

场景分类 v2 system prompt =
  角色：万邑通入库/库内/出库增值审核场景分类器
  任务：根据客户需求描述和已知上下文，从候选场景中选一个或 unsupported
  候选：规则 topK/补齐到最多 15 张场景卡
  规则：异常单详情优先；规则 A/B/C/D；入库/库内/出库边界；不要编造 sceneKey
  输出 JSON：matchedScene, topicSummary, matchedSceneName, confidence,
             reasoning, conclusionOneLiner, extractedActions, alternativeScenes, ambiguous

L2.5 信息完整性 user prompt =
  角色：增值审核完整性检查员
  输入：场景 requiredInfoFields、客户需求描述、已上传附件、系统已掌握的单据信息
  判断标准：原文直接写了/上下文可推断/OMS 字段或附件线索已有 => 有；否则缺失
  输出 JSON：{"checks":[{"field":"处理范围","present":true,"evidence":"264箱"}],
             "missing":["辨识方法未说明"]}

文件型 Prompt 全文入口

下面是实际文件 prompt 的作用摘要；完整文本就在对应文件中，HTML 已保留路径，便于你后面直接改。

prompts/sop-generate.md
- 角色：万邑通入库非标增值 SOP 撰写专家
- 硬约束：只引用输入事实；不得写审核通过；处理方式为“暂时”；不得编造单号/SKU/数量
- 内容禁区：不写系统按钮、不写客户/销售/客服动作、不写费用/SLA
- 输出 JSON：requirementDescription, requirementBackground, warehouseSop, sopText,
             scenarioName, fieldsUsed, extractedWiNumbers, extractedEbNumbers

prompts/sop-reflection.md
- 检查：事实编造、遗漏、禁词、操作完整性、可执行性、系统界面编造、非仓库职责
- 输出：PASS 或 issues JSON

prompts/requirement-clarification.md
- 需求描述不完整时发客服/销售
- 不生成 SOP，不代填事实，不自动审核

prompts/field-clarification.md
- 场景已确认但缺关键信息/附件时发客服/销售
- 一次说完信息和附件

prompts/transfer-human.md
- 规则判定不能自动处理时给审核员的 1-3 句理由

prompts/summarize-reply.md
- 把 AI 首判、原始需求、飞书回复总结为可复制 OMS 备注

Badcase 定位手册

  1. 先看 outputPath、node、failureGate： needs_requirement_clarification 是 L1，needs_field_clarification 是 L2.5， sop_generated 是 L4，llm-generate-sop 是 SOP 生成失败。
  2. 场景错：看 matchResult.candidates/topK。如果规则候选里没有正确场景，改 scenario-cards 的 positive/negative/boundary；如果候选里有但 LLM 选错，改 场景分类 prompt 的边界规则或开启/补充 RAG few-shot。
  3. 明明信息齐却追问：看 sceneCompletenessResult.infoChecks 和 contextFacts.knownFactLines。如果已知事实没进 prompt，改抽取/绑定；如果字段定义过严，改场景卡 requiredInfoFields。
  4. 附件误判：看 attachmentStatus 和 requiredAttachmentPolicy.requiredFieldKeys。 附件不是 LLM 判断，优先改文件名识别、附件字段映射或场景卡附件策略。
  5. SOP 事实编造/步骤错：看 llm.sop、reflectionIssues、degraded。 修法通常在 sop-generate.md、SOP KB 模板、场景卡 sopTemplateHints。
  6. 写入失败或看板闭环异常：看 oms_write_fail、failureType、 writeResult.skipped。这通常不是 AI 能力问题，而是状态、allowlist、人工 SOP 已填或 OMS 接口问题。

对看板指标的启发

这条链路天然适合按“节点漏斗”监控，不适合只看一个场景识别准确率。 我建议北极星仍围绕 AI 一次性草稿可用率 或 AI 草稿一次通过率， 往下拆成：L1 需求拦截率、场景识别通过率、L2.5 信息完整率、SOP 生成成功率、OMS 写入成功率、 人工修改距离/审核员反馈 badcase 桶。

当前代码已经有这些埋点的雏形：nodesHit、ruleOutputPath、outputPath、 failureGate、matchResult、sceneCompletenessResult、llm.reflectionIssues、 appendAiWriteSnapshot 和 syncAuditDiff。看板后续可以直接按这些字段做层层下钻。
