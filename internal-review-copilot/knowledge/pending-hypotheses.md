## H1：异常名称硬映射在补拉 events 后是否成立

**验证方法：** 对 §2.33 的 76 单补拉 OMS `getEventOrders` 获取异常名称，重跑交叉统计。

**当前状态：** 未验证。时间修正后仍不成立，但样本偏置严重。

**所需资源：** OMS 异常单详情 API 访问权限。

**来源：** `_runs/20260909_p3_eval/exception-scene-mapping-probe.md`、`scene-trend-by-month.md`

## H2：需求复杂度是 §2.1 vs §2.33 的分流因子

**假说：** 简单需求（字数≤284、动作数≤2）走 §2.33，复杂需求走 §2.1 兜底。

**当前状态：** 部分成立。方向对但样本小（§2.33 只有 1 单带需求描述）。

**验证方法：** 补拉 §2.33 的 76 单的需求描述和附件，重跑复杂度对比。

**潜在用途：** 如果成立，match-template 可以加"需求复杂度"软权重——简单的加 §2.33 分，复杂的不加。

**来源：** `_runs/20260909_p3_eval/complexity-vs-scene.md`、`complexity-boxplot-scene-cache.png`

## 已验证：Phase 2 四版对比基线（2026-09-09）

| 指标 | Phase 1（纯规则） | v1（LLM 无异常查询） | v2（LLM+预查异常+硬规则） | v3（LLM+自主工具调用） |
|------|----------------|-------------------|----------------------|---------------------|
| 场景精准匹配 | 1/5 (20%) | 2/5 (40%) | 4/5 (80%) | 4/5 (80%) |

## H8：按客户编码自动拉取销售/客服 → 飞书话题自动 @人

**假说：** pipeline 新建飞书话题时，可以根据增值单的客户编码自动查到对应的销售和客服，直接 @他们到话题里，不需要人工指定。

**已验证可行：** DWS 表 `bi_dw.dim_bpartner_account_info_t` 按 `winit_account_id` 可查：
- `salesman` / `salesman_name` — 销售代表（覆盖率 ~100%）
- `service_user_name` — 客服代表（覆盖率 ~62%）

**示例 SQL：**
```sql
SELECT winit_account_id, name_cn, salesman, salesman_name, service_user_name, service_user_id
FROM bi_dw.dim_bpartner_account_info_t
WHERE winit_account_id = '<客户编码>'
```

**实现方案：**
1. 预拉取：定期从 DWS 导出客户→销售/客服映射表，存为 JSON，pipeline 启动时加载
2. 实时查：pipeline 运行时调 DWS 查（延迟 ~1s，可接受）
3. 查到销售/客服姓名后，用飞书通讯录 API 查 open_id，再 @人

**当前状态：** 已验证数据可用。未接入 pipeline。Demo 阶段用假设人员。

**来源：** Cursor 探测 winit-data DWS，2026-09-09
