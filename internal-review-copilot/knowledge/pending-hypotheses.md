## H8：按客户编码自动拉取销售/客服 → 飞书话题自动 @人

**假说：** pipeline 新建飞书话题时，可以根据增值单的客户编码自动查到对应的销售和客服，直接 @他们到话题里，不需要人工指定。

**已验证可行：** DWS 表 `bi_dw.dim_bpartner_account_info_t` 按 `winit_account_id` 可查：
- `salesman` / `salesman_name` — 销售代表（覆盖率 ~100%）
- `service_user_name` — 客服代表（覆盖率 ~62%）

**示例 SQL：**
```sql
SELECT winit_account_id, name_cn, salesman, salesman_name, service_user_name, service_user_id
FROM bi_dw.dim_bpartner_account_info_t
WHERE winit_account_id = '<客户编码>'
```

**实现方案：**
1. 预拉取：定期从 DWS 导出客户→销售/客服映射表，存为 JSON，pipeline 启动时加载
2. 实时查：pipeline 运行时调 DWS 查（延迟 ~1s，可接受）
3. 查到销售/客服姓名后，用飞书通讯录 API 查 open_id，再 @人

**当前状态：** 已验证数据可用。未接入 pipeline。Demo 阶段用假设人员。

## H9：Slot Filling — 跨轮渐进式信息补全

**需求：** 客户首轮提交的需求描述通常不完整。当前 L2.5 每轮全量检查、一次列出所有缺的信息。业务方反馈追问太多销售不看。

**设计方向：**
- CaseRecord 加 `slots` 字段，per-case 跟踪每个槽位的填充状态（filled/missing/asked）
- 每轮只检查未填的槽位，不重复检查已填的
- 每轮最多追问 1-2 个最关键的（必填优先，可选后问）
- 补了一个就少追问一个，飞书卡片展示"已确认 ✓"和"待补充 ❓"

**改动范围：** types.ts（CaseRecord.slots）、check-scene-completeness.ts（传入上轮状态）、poll-and-assess.ts（读写槽位）、feishu-card.ts（分段展示已填/未填）

**当前状态：** 设计完成，未实现。归入 V2 迭代，不阻断 V1 部署。

## H11：SKU 一致性自动校验（原单拦截场景）

**需求：** 审核主管反馈 VASC000000370434：客户原入库单包裹被拦截，要上架到新入库单。AI 需要自动校验原单被拦截包裹的 SKU 与新入库单 SKU 是否一致。

**触发条件（规则）：**
- 场景 ∈ {包裹条码批量异常, A+包裹换标, 包裹类异常换商品标签}
- 需求描述匹配 (原单|原入库单|拦截|截.*上架) + 新 WI 号

**实现方式：**
1. 从 EB 异常单查原入库单被拦截包裹的 SKU 列表；没有则 DWS 按 WI 查
2. 从新 WI 号查新入库单的 SKU 列表
3. 比对结果做成审核员提示「【提示：本单AI识别到……请审核人员关注】」，展示在飞书卡片，**不写入仓库 SOP**

**当前状态：** 已实现（卡片提示审核员；VASC000000370434 实测 mismatch 377 vs 21）。
**来源：** 2026-09-16 审核主管反馈，VASC000000370434；2026-09-17 改为审核员提示而非 SOP 步骤。

**优先级：** 下个版本迭代。2026-09-17 金萤：本会话只优化 40 线上小细节，H17 **本会话不排期、不改代码、不上 40**。

### 背景（为什么要做）

橙卡请销售/客服补信息后，他们会在**【增值】异常沟通**的话题里直接回文字，也可能丢**图片/附件**（标签样例、圈注、操作说明图）。金萤要的闭环是：

1. **不必 @ 智能体**也能收到补充。
2. 用 pipeline 的 **L2.5 `check-scene-completeness`** 再判「关键信息齐不齐」。
3. **齐了就自动进下一节点**：生成 SOP，能写 OMS 就写（不点审核通过）。
4. 还缺 → 仍在**同一话题**更新橙卡，只 @ 销售/客服，不 @ 李颖 / 何静 / 耿文文。

这和 H14 不同：H14 是读 **OMS 里已上传的文件正文**；H17 是读 **飞书话题里刚补的内容**，再决定能不能出 SOP。

### 三条接法共用的判断逻辑（未实现）

1. 话题里出现销售/客服**新消息**（文字或图片），不必 @。

### 方案 A：仍用 10 分钟大轮询（改最小）

**怎么跑：** 继续 `poll-and-assess --interval 600`。现有 `refreshReplies` 已能发现「有人回了字」。补：下图 → 认图 → 「飞书补充」进 L2.5 → 齐了出 SOP。

**优势：** 改得少；飞书调用少。  
**劣势：** 补完最多等一轮（约 10 分钟），现场会觉得没反应。

适合：先验证认图+喂 L2.5，不在乎等几分钟。

### 方案 B（推荐）：橙卡话题也走 12 秒轮询

**怎么跑：** listen 里已有 SOP 修改的 12 秒扫话题（不必 @）。把同一套路扩到橙卡状态（`needs_clarification` / `needs_attachment` 等）。10 分钟大轮询仍只拉 OMS 新单。认图与「齐了出 SOP」同共用逻辑。

**优势：** 不用 @、不抢卡片总线，补完大约十几秒就能判、能出 SOP；和现成 `sop_editing` 轮询同一套路。  
**劣势：** 橙卡多时 12 秒扫会打飞书接口，必须**只扫还在等补充的单**。

适合：正式体验——群里一补，很快进下一节点。金萤侧推荐。

### 方案 C：再开实时 IM 监听

**怎么跑：** `LISTEN_IM=1`，人一回立刻处理。飞书同一应用一条事件总线，现网注释：**开会把卡片按钮顶掉**。要实时又要点按钮，只能**新建独立飞书应用**（新 slug / 新 `cli_`），40 只新建、不改现有增值咨询。

**优势：** 最快。  
**劣势：** 要么卡片点不了，要么多一套应用和部署。

**不推荐第一刀。**

## H19：专业销毁非标询价（OSF8V1848）独立原子闸

**假说 / 现网缺口：** 客户出库选专业销毁时必下一张 `OSF8V1848`。专家审核的核心不是写仓库操作步骤，而是：站点+商品属性下这条销毁合不合规、有没有更便宜合规的路（弃置 / 仓内销毁 / 换专业细类）。现网 Copilot 只扫入库/库内其他服务需求，销毁询价单直接跳过。

**会上已对齐的硬规则（待接口验证）：**

- 仓内销毁仅美国站普货；电子元器件/金属/液体不行；德澳加英不行。
- 专业销毁三类：普货 / 危废 / TS 合规；TS 必须能在商品备案管理查到备案。
- 化工/食品/纯电不能走普货专业销毁。
- 普通货（枕头例）可选专业销毁，但贵；应建议更便宜路径，不要当违规驳回。
- 弃置会把处置权交给万邑通，**不能自动改客户已选项**。

**推荐落点：** 方案 A = 像 T1 的独立原子闸，不进场景卡。第一刀只做「美国普货误下专业销毁 → 橙卡建议仓内/弃置」+「非美不要推荐仓内」。危废/TS 后补。
