# 需求完整性：权威来源与 pre-match 最低可路由门

本文件是内部审核 Copilot 对「需求是否够往下走」的口径说明。  
**权威原文只在一处，本文件只做索引和映射，不复制模板正文。**

## 权威来源

需求完整性抽象必须以《非标增值服务SOP模板 及 填写示例》为准：

`workspace/knowledge/sop/非标增值服务SOP模板及填写示例.md`

不要把 `check-requirement` 里的三槽当成权威标准。三槽只给 trace 展示，L1 只拦空白。场景级齐套看 scenario card + L2.5。

完整 SOP 结构（权威模板栏目）包括：

| 栏目 | 在权威模板中的位置 |
|------|-------------------|
| 场景概述 | 文首 |
| 客户名称 | 文首 |
| 业务单据 | 文首 |
| 商品SKU | 文首 |
| 需求背景 | 文首 |
| 操作目的 | 一 |
| 适用范围 | 二 |
| 操作步骤 | 三（含操作说明 / 注意事项 / 工具/材料） |
| 关键输出 | 四 |
| 异常处理 | 五 |
| 附件要求 | 六 |

客户名称、业务单据、仓库等若已由 OMS / `context-bind` 注入，不再当作需求追问项。

## check-requirement 是什么、不是什么

| 是 | 不是 |
|----|------|
| `match-template` 之前的 **L1 极简兜底**（空白/过短才拦） | 完整 SOP 校验器 |
| 场景无关：不先套任何 scenario card | 最终需求完整性标准 |
| 三要素正则仍提取给 trace，**不再阻断** | 数量、范围、材料、工具、附件、关键输出、异常处理的齐套检查 |

完整 SOP 校验以后由这些节点承担：

1. `match-template`——命中具体场景
2. `check-scene-completeness`（L2.5）——该场景 `requiredInfoFields`（LLM）+ 附件/真字段（规则，复用 `check-completeness`）
3. `llm-generate-sop`——按权威模板栏目成稿

## 当前 L1 门

按审核页**有没有「需求描述」格子**分支（看 `vaAtomAttrs` 名单，空值也算有格子）：

| 审核页 | L1 |
|----|----|
| **有**需求描述格子，空或过短 | 拦，橙卡「请填写需求描述」 |
| **没有**需求描述格子 | 不拦；用已填格子 + 异常单拼给模型写 SOP；OMS 不写需求描述 |
| 没有格子，且其它格子/异常单也几乎没有 | 转人工（不是请补需求描述） |

「需求背景说明」同样：没格子不写、不拦；有格子没填不单独当 L1 橙卡（仍看需求描述格子那条）。

`lib/check-requirement.ts` 在「有格子」分支才输出 `需求描述为空或过短`。

三槽（对象 / 动作 / 背景·目的·去向）仍匹配并写入 trace，缺槽也不再拦截。场景级信息齐套改由 L2.5 按卡追问。

## 明确不是 pre-match 硬缺失项

下列栏目属于完整 SOP，**不得**在所有场景的 `check-requirement` 里当成硬缺失项；进入具体 scenario card 后再校验：

- 数量、范围（模板「适用范围」里的量化信息）
- 材料、工具（模板「操作步骤」里的工具/材料）
- 附件（模板「附件要求」）
- 关键输出
- 异常处理
- 对象对应关系 / 标签映射（场景专属，交给 L2.5 `check-scene-completeness`）

禁止再输出 `数量或范围`、`对象对应关系` 这两个 `missingRequirementItems`。

## 完全看不出时怎么归

若需求文本几乎看不出作业，例如「帮我处理一下」：

- L1 **放行**（有内容）
- 进 `match-template`；匹配成功后由 L2.5 按场景追问缺什么
- **不要**在 L1 输出 `数量或范围` / `操作动作不清`
