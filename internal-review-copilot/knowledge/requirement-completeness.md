# 需求完整性：权威来源与 pre-match 最低可路由门

本文件是内部审核 Copilot 对「需求是否够往下走」的口径说明。  
**权威原文只在一处，本文件只做索引和映射，不复制模板正文。**

## 权威来源

需求完整性抽象必须以《非标增值服务SOP模板 及 填写示例》为准：

`workspace/knowledge/sop/非标增值服务SOP模板及填写示例.md`

不要把 `check-requirement` 里的三槽当成权威标准。三槽是从该 SOP 模板**抽象出的 pre-match 最低可路由门**，只回答「现在能不能进 `match-template`」，不回答「SOP 是否写全」。

完整 SOP 结构（权威模板栏目）包括：

| 栏目 | 在权威模板中的位置 |
|------|-------------------|
| 场景概述 | 文首 |
| 客户名称 | 文首 |
| 业务单据 | 文首 |
| 商品SKU | 文首 |
| 需求背景 | 文首 |
| 操作目的 | 一 |
| 适用范围 | 二 |
| 操作步骤 | 三（含操作说明 / 注意事项 / 工具/材料） |
| 关键输出 | 四 |
| 异常处理 | 五 |
| 附件要求 | 六 |

客户名称、业务单据、仓库等若已由 OMS / `context-bind` 注入，不再当作需求追问项。

## check-requirement 是什么、不是什么

| 是 | 不是 |
|----|------|
| `match-template` 之前的 **pre-match 最低可路由门** | 完整 SOP 校验器 |
| 场景无关：不先套 F-001，也不先套任何 scenario card | 最终需求完整性标准 |
| 只判断「对象 / 动作 / 背景·目的·去向」是否足以理解作业并分流 | 数量、范围、材料、工具、附件、关键输出、异常处理的齐套检查 |

完整 SOP 校验以后由这些节点承担：

1. `match-template`（及后续 scenario card，本次未做）——命中具体场景
2. `check-completeness`——该场景下的附件 / 真字段
3. `llm-generate-sop`——按权威模板栏目成稿（需求背景、操作目的、步骤、关键输出、异常处理、附件等）

## 当前 pre-match 最低门（三槽）

从权威模板抽出、且**所有场景共用**的最低可路由条件只有下面三条。实现见 `lib/check-requirement.ts`。

### a. 能否看出处理对象

对应模板：业务单据、商品SKU，以及正文里的商品 / 包裹 / 箱 / 库位 / 附件上下文。

可来自需求文本，或已绑定的 EB / WI。  
看不出时输出：`操作对象不清`。

### b. 能否看出处理动作

对应模板：操作目的、操作步骤里的动作（拍照 / 暂存 / 换标 / 上架 / 拦截等）。

看不出时输出：`操作动作不清`。

### c. 能否看出需求背景、操作目的或处理去向之一

对应模板：需求背景、操作目的、适用范围里的去向（为什么做、做到什么结果、处理后去哪里）。

三者有其一即可过门。已绑定的 WI / EB 可充当去向，不再追问。  
都看不出时输出：`需求背景/操作目的/处理去向不清`。

## 明确不是 pre-match 硬缺失项

下列栏目属于完整 SOP，**不得**在所有场景的 `check-requirement` 里当成硬缺失项；进入具体 scenario card 后再校验：

- 数量、范围（模板「适用范围」里的量化信息）
- 材料、工具（模板「操作步骤」里的工具/材料）
- 附件（模板「附件要求」）
- 关键输出
- 异常处理
- 对象对应关系 / 标签映射（场景专属，交给 `check-completeness`）

禁止再输出 `数量或范围`、`对象对应关系` 这两个 `missingRequirementItems`。

## 完全看不出时怎么归

若需求文本无法判断范围或对象，例如「帮我处理一下」：

- 归入 `操作对象不清` 和 / 或 `操作动作不清`
- **不要**输出 `数量或范围`

「完全看不出」≠「没写件数」。正文已有包裹 / SKU / 单据 / 库位，或上下文已绑定 WI / EB，就不要因为没写 N 件而挡在 pre-match。
