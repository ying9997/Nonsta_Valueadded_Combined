# 计划：expert 用标识跟前端通信（不改发消息方式）

- 日期：2026-09-17
- 状态：讨论已对齐目标与风险；**未授权改现网对话 Bot / Query / recaller**
- 所属：`Nonsta_Valueadded_Combined/cs-eds-page-bridge`（通道）+ 后续增值审核 expert
- 一句话：前端还是对对话 Bot 发消息；出卡/读页/点页的数据用一段带标识的内容塞在 expert 输出里，两边看见标识再拆。先证明这段内容走完对话流还在，再谈上线。

---

## 1. 要做成什么样

卖家在 EDS 页侧栏照旧聊天。AI 需要出卡、读当前页、点页面时，不另开一套发消息方式。

| 方向 | 做法 |
|---|---|
| AI → 前端 | expert 节点输出里带一个**标识**，后面塞出卡 / 读页 / 点页数据。打到对话 Bot 的回复里如果出现这个标识，前端就解析，不要当普通客服话。 |
| 前端 → AI | 前端回给 Bot 的内容也加同一类标识。expert 后面再拆。 |
| 格式 | 第一期不追求严谨 schema，能拆开、能对上即可。 |
| 前端进度 | 不阻塞：可以先把标识和样例数据放进 expert 工作流；**但现网客服 Bot 要等对话流证明「标识没被改掉」再绑。** |

人话气泡照旧给卖家看。标识包是给前端机器看的，不要指望卖家去读 JSON。

---

## 2. 已经确认的事实（不是猜测）

对话一层套一层：

```
EDS 侧栏聊天
  → 对话流 cs_Bot_Client_v2p_1
    → 子流程 Query（真正问答）
      → 需要专家时 experts_recaller
        → 各个 expert
```

一条真实问题从 expert 出来之后，还会经过这些格，**不是原样送到聊天气泡**：

| 顺序 | 节点 | 对标识包做什么 |
|---|---|---|
| 1 | expert 结束节点 | 一般能原样吐出你塞进去的内容 |
| 2 | experts_recaller | 只往下交一句 `reply_to_user`；会再总结成人话。`structured` 整包带不出去 |
| 3 | A1「拼装问题资料并组织回答」 | 大模型按「解读专家 json」重写成对客句子，**最容易把标识改掉或拆碎** |
| 4 | Query 中途「输出」节点 | 用户和前端看到的是这里发出的话，不是 expert 原文 |
| 5 | tools_msg_cleaner | 清对话历史里的程序符号，花括号 / 代码块可能被清 |
| 6 | Query 结束节点 | **不往 Bot Client 带字段** |

因此：只把标识塞进 expert 工作流并发布专家本身，**不等于**前端已经能从对话 Bot 里解析到原样数据。

画布出处：`ai/agentic/Coze工作流导出/Chatflow-cs_Default_Query_v4_staging_D_1-draft-5799/`（线上 Query 是 staging_F 同结构）。

另：`D:\DA\experts` 里目前**没有**「增值审核 / 帮卖家填单」这个 expert 包。线上已有的是增值指引 / 状态 / 推荐等，不是这件事。

## 3. 这次选定的通道（相对旧方案）

之前 `cs-eds-page-bridge` 走的是：对话流末尾 `tool_call_send`（`pageRead` / `renderA2UI`），前端用 `queryToolCall` 拿口令。

这次讨论选定的是另一条、更省前端改动的通道：

- 前端**不改**怎么给 Bot 发消息（还是聊天）。
- 通信数据跟在对话回复 / 下一轮用户输入里，靠**标识**区分。
- 格式先松。

旧的 `tool_call_send` 接线（对话流副本 `7685975376836739124`）先留着当备胎，本计划不拆、不绑现网。两条通道不要混在同一期验收里。

## 4. 明确不做（本期）

- 不改现网对话 Bot（旧画布 `7685663589169381391`）
- 不改现网 Query / recaller，除非第 1 步证明必须改，并且另行点名授权
- 不上 server-40
- 不把 Copilot 飞书审核通过率当成客服 expert 已可上线
- 不追求场景 / SOP / 填单字段正确（那是下一阶段）
- 不把页面口令写进 `qa-gen_base.csv`

## 5. 分步（按顺序，前一步没绿灯不做后一步）

### 第 0 步 — 对照三处：真实问题走完，标识还在不在

**目的：** 回答你最关心的问题，不靠猜。

用一条会召回专家的真实客服问题，打**测试 Bot**（不要打现网）。对照：

| 看哪里 | 过关标准 |
|---|---|
| expert 结束节点原文 | 标识 + 数据完整 |
| recaller 的 `reply_to_user` | 标识还在或已经丢（记下来） |
| A1 输出 / 聊天气泡 | 标识和数据仍能被程序拆出来 |

预期（按现画布）：到 A1 / 气泡就已经没了。若意外还在，第 2 步可以很轻；若没了，必须做第 2 步，不能直接上线。

没有现成增值审核 expert 时：先在**测试空间**用一个可召回的现有 expert，或 expert 工作流单独运行 + 再走一遍 Query，不要绑现网。

### 第 1 步 — 定一个够用的松标识

第一期只定三件事，schema 以后再收紧：

1. **起止标记**一眼能扫到，普通客服话里几乎不会撞车（例如固定头尾行，而不是随手一个 `#`）。
2. **包里有类型**：至少能区分 `出卡` / `读页` / `点页结果` / `前端回传页面`。
3. **人话和包分开**：卖家气泡里尽量只留人话；标识包可以紧跟在人话后面，或单独一段。若只能先混在一段里，前端按标记截取，A1 仍可能改写中间 JSON。

内容第一期可以先塞现在的样例：`cs-eds-page-bridge/fixtures/sidecar-render-a2ui.json`、`sidecar-page-read.json`。对不上 catalog 的卡片，前端可以后画，但标识必须能被看见。

### 第 2 步 — 若第 0 步证明被改：做「原样带出」而不是指望 A1 手下留情

不要把希望放在「改 A1 提示词让它别动 JSON」——大模型不稳定，cleaner 还会再清一层。

候选（第 0 步之后点名一条，不要三条一起做）：

| 候选 | 做法 | 优点 | 缺点 |
|---|---|---|---|
| A（推荐先想） | 标识放 expert `structured`；Query 结束或会话变量**原样**带到对话流出口；人话仍走 A1 | 人话和机器包分开，卖家看不见 JSON | 要改 Query 出口或会话变量，需点名授权 |
| B | 本专家走 Query 旁路，A1 不经过，结束节点直接吐 expert 原文 | 改动面相对清楚 | 气泡里可能出现机器字；其它专家不受影响但要加分支 |
| C | 继续用已接好的 `tool_call_send`，标识通道放弃 | 前端 SDK 已按口令设计 | 和「不改发消息 / 解析气泡」不一致，需和前端重新对齐 |

未做第 0 步之前，不改 Query 画布。

### 第 3 步 — 把标识和样例数据放进 expert 工作流

只在**测试空间**发布专家工作流，验证结束节点能吐出标识包。

- 有审核 expert 包：放在它的结束输出里。
- 还没有：先建最小 expert（能进 recaller、能吐标识 + 假数据），或用现有 expert 加一段试点输出。  
  **完整审核流水线 / SOP 准确不是这一步的范围。**

验收：只跑这个 expert 工作流（不经过 Query）时，结束节点里标识 + 数据完整。

### 第 4 步 — 测试对话 Bot 里「标识能被解析」

测试 Bot 指向带试点的对话流副本，不要指向现网旧画布。

- 出：气泡或约定出口里能扫到标识，样例出卡/读页数据能 parse。
- 回：下一轮用户消息带标识（可先手贴），expert 侧能拆出「这是前端回传」。
- 前端可以还没改：用预览里手贴标识模拟即可。

### 第 5 步 — 才谈上线

同时满足才允许把这个 expert 接到**现网**智能客服工作流：

1. 第 0 / 4 步绿灯：真实问题走完对话流，标识包仍能被程序拆出来。
2. 测试 Bot 上：出方向、回方向各至少 1 次成功（前端接上或手贴模拟均可）。
3. 普通问答（不带标识）回复不被污染、不被误解析。
4. 现网 Bot 绑定是单独一次点名操作，不是「专家工作流发布了就自动上」。

---

## 6. 和「增值审核 expert 上线」的关系

本计划只解决：**标识通道会不会被对话流吃掉，以及怎样原样带到前端能解析的地方。**

审核专家要上线另外还缺（本计划不展开做）：

- 把 Copilot 流水线做成 `experts/` 统一 I/O 的 expert 包
- qa-gen / recaller 能召回
- 场景和填单准确（阶段二）

通道没绿灯，审核 expert 即使做完，前端也拿不到出卡/读/点指令。
